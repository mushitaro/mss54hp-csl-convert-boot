# ブートローダ置換 — 確定した機構と、危険の所在

標準 M3 のブートローダ (`21132300`) を CSL のもの (`21132500`) に置き換えるための、
**実測で確定した事実**をまとめる。既存の [`bootloader-and-obd-reflash.md`](bootloader-and-obd-reflash.md) と
[`security-access-cmd90-91.md`](security-access-cmd90-91.md) には**誤りがある**。本書がそれを訂正する。

すべて、実バイナリの逆アセンブルと、**8 本の実イメージ**の突き合わせによる。

| # | イメージ | 素性 |
|---|---|---|
| 1 | `Full 211323000401PD31_TERRA.bin` | CSL 0401 を `211323` に改名した TERRA 改造版 |
| 2 | `data/211325000401PD31_Community_Patch_v1.bin` | コミュニティパッチ v1 |
| 3 | `hw2001-analysis/hw2001_full.bin` | **標準 M3 の実車ダンプ** |
| 4–7 | `data/genuine-csl/ZB78373*.bin` | **BMW 出荷の純正 CSL ECU ダンプ** (YulCmr、2004-12-21) |

---

## 1. 素性は決着した — CP v1 の BL は BMW 純正 CSL BL そのもの

`bootloaderImage.test.ts` が固定している実測結果:

- 純正 CSL ダンプ 4 本の SA0 は、master・slave とも **CP v1 と 1 バイトも違わない**。
- 同 4 本は標準 M3 の SA0 と **ちょうど 6 バイト (master) / 3 バイト (slave)** だけ違う。
- 標準 M3 の SA0 にその 6/3 バイトを当てて CRC を再計算すると、
  **純正 CSL SA0 とバイト一致する**。

⇒ 「再構成」と「純正」は**同一のバイト列**。CP v1 のブートローダは本物である。

### CSL BL は 1 種類しかない — そして書くのはその定数 (2026-09-04 追加)

手元の全イメージで SA0 は **2 種類しか存在しない**:

| SA0 (master/slave sha256 先頭) | 該当 |
|---|---|
| `a5d75cc9…` / `ebb52919…` = **CSL** | 純正 BMW CSL ダンプ 4 本 (CSL cams / stock cams / No-EOBD / Japan) + CP v1 (21132500) |
| `60a9abf6…` / `23d03e70…` = **標準 M3** | CP v1 (21132300) / TERRA / repair |

較正も市場も違う 4 台の純正ダンプが一致する。さらに **7 本の標準 M3 SA0 のうち 6 本**が
`patchToCsl` で CSL 側にバイト一致で到達する (実車 4 台、プログラム版 1801 / 2001 / 2501 を含む)。

⇒ **CSL SA0 は定数であり、かつ導出でも再現できる。**

### ⚠ 実車で 1 台、参照に無いバイトが見つかった

ある実車 (プログラム版 2001) の slave SA0 だけ、`0x3FE4`–`0x3FE9` に `82 79` ×3 を持っていた。

- **slave の CRC は `0x0000`–`0x3FE1` しか覆わない**ので、この領域は BMW 自身の検査を素通りする。
  だから何年も気づかれない。
- 純正 CSL 4 本にも、標準 M3 の参照 3 本にも、**この位置に `FF` 以外は無い**。
- コードではなく、BMW 流の ×3 識別フィールドの形をしている。

導出のみの設計では、これが**警告も無く新しいブートローダに焼き込まれる**。SA0 は BDM でしか
戻せないセクタなので、それは許容できない。

### 方針: 導出は検査として残し、書くのは参照

`patchToCsl(sa0, processor, reference)` に参照 SA0 を渡すと:

- **書かれるのは参照側の値**。車固有の異常は引き継がれない
- **導出は実行され続ける**。これは provenance の議論そのもの — このツールは目の前の車から
  再構成できないブートローダを持たない
- 食い違いは `anomalies` として返り、REVIEW に**引き返せない警告より上**に表示される。
  CRC 範囲外かどうかも出る (「BMW の検査を素通りしていた」= 古い可能性が高い、の合図)

参照は `packages/web/public/bootloader/csl-sa0.bin` (32 KiB、SA0 のみ。SA1 は車固有なので含まない)。
`bootloaderReference.test.ts` が 5 系統との一致を固定している。参照が取得できない場合は
**従来どおり導出のみで続行**し、失われるのは検査だけである。

### 差分の全て

| CPU | オフセット | 標準 M3 | CSL | 意味 |
|---|---|---|---|---|
| master | `0x12AE` | `E0` | `F0` | `tst.b $8E002` → `tst.b $8F002` |
| master | `0x3FD7/DF/E7` | `'3'` ×3 | `'5'` ×3 | `"21132300"` ×3 → `"21132500"` ×3 |
| master | `0x3FFE-FF` | `E2C3` | `3C45` | CRC |
| slave | `0x12AE` | `E1` | `E0` | `tst.b $8E102` → `tst.b $8E002` |
| slave | `0x3FE2-E3` | `EABA` | `6465` | CRC |

master と slave は**別ビルド** (同一イメージ内で 0x0–0x3FFF が 225 バイト相違)。
master は ID タグ `0x3FFC`=`"MM"`、slave は `0x3FE0`=`"SS"`。
**slave の BL に型番文字列は無い** — slave の素性は SA1 の `0x5DB4` が持ち、そこは車両固有。

### `0x12AE` の機能

```
0x12AA: tst.b  $8F002        ; CSL (M3 は $8E002)
0x12B0: beq    $12B6
0x12B2: addi.b #$C, d2       ; d2 (DS2 応答長) += 12
0x12B6: btst   #2, $FFD001
0x12C0: addq.b #2, d2
0x12C6: move.b d2, d0
```
**DS2 ident 応答に 12 バイト足すかどうか**だけ。走行性能には無関係。

## 2. SA0 の整合検査は CRC-16/ARC (鍵ではない)

| | 範囲 | 格納位置 |
|---|---|---|
| master | `0x0000`–`0x3FFD` | `0x3FFE` (BE) |
| slave | `0x0000`–`0x3FE1` | `0x3FE2` (BE) |

較正ペアと同じ算法。**8 イメージ 16 面すべてで自己整合**。
CRC テーブルはファーム内 `0x37EC` にある。

DS2 制御 `0x0A` (encoding checksum) は **bit0 = master ブートセクタ / bit4 = slave ブートセクタ**
の健全性を報告する (**立っていれば異常**)。書込前後の判定に ECU 自身が使える。

## 3. セクタ地図とニブル→物理アドレス (ファームから復元)

チップは Am29F400BB (bottom boot)。write ハンドラ (`0x264E`–`0x26C6`) が
`0x2690` の値表と `0x2672` のジャンプ表で `a2` に**物理ベースを直接置く**:

| ニブル | 物理ベース | セクタ | サイズ |
|---|---|---|---|
| `0x0`/`0x8` | `0x4000` | SA1 Free Identifiers | 8K |
| **`0x1`/`0x9`** | **`0x0000`** | **SA0 ブートローダ** | **16K** |
| `0x2`/`0xA` | `0x88000` (=flash `0x8000`) | SA3 較正 | 32K |
| `0x3`/`0xB` | 拒否 `0xB0` | DPRAM (`0x13F800`) | 2K |
| `0x4`/`0xC` | `0x6000` | SA2 ガード | 8K |
| `0x5`/`0xD` | `0x10000` | SA4–SA10 プログラム | 448K |
| `0x6`/`0xE` | 拒否 `0xB0` | RAM | — |

参照実装 `Ds2ProgrammingSubsegment.cs` の enum
(`FreeIdentifiers 0 / BootBlock 1 / DataBlock 2 / Dpram 3 / EepromEmulation 4 / ProgramBlock 5 / Ram 6`、
slave = master+8) と**完全一致**。実車実証済みの較正 `0x2`/`0xA` とプログラム `0x5`/`0xD` も
この表で正しく解決される。**独立 3 系統で一致**。

SA1 には**アプリ入口ベクタ `0x4884`**、フラッシュカウンタ `0x4800`、VIN `0x5D50` がある。
配布イメージはここが全て `0xFF` に消されているので、**失うと車両のバックアップからしか戻せない**。

## 4. ⚠ 消去はできないが、**無消去書込は通ってしまう**

消去ハンドラ (`0x2464`/`0x2516`/`0x2590`) は `d3 = req[4] & 0xF0` の許可リスト:

- `{0x50, 0xD0, 0x00, 0x80}` → セッション状態 `0xFFD00E = 0x66`
- `{0x20, 0xA0}` → `0xFFD00E = 0x3C`
- **それ以外は拒否。ニブル `0x1` は入っていない。**

> 副産物: **ニブル `0x5`/`0xD` (プログラム 448K) の消去は明示的に許可されている**。
> `write-process.md` §7(a) の「全ての前提」はファーム側の答えとしては **YES**。

一方、書込ハンドラ (`0x2730`–`0x2798`) は**より緩い**:

| `0xFFD00E` | 許可ニブル |
|---|---|
| `0xC3` | `0x00`, **`0x10`**, `0x40`, `0x80`, **`0x90`**, `0xC0` |
| `0x66` | `0x50`, `0x00`, `0xD0`, `0x80` |
| `0x3C` | `0x20`, `0xA0` |

`0xC3` は **Finish (seg `0x0F`) を通った後**に設定される (`0x2452`)。つまり
**通常のフラッシュセッションの後片付けの後、ブートローダへの seg `0x02` (無消去書込) が受理される**。

NOR の書込はビットを 0 にしかできず、**SA0 は DS2 では消去できない**。
⇒ **ブートローダに 1 ビットでも誤って書いたら、BDM 以外に復旧手段が無い。**

本ツールは `telegrams.ts` の `eraseNibbleAllowed()` / `writeNibbleAllowed()` で
**両方ともニブル `0x1`/`0x9` を無条件に拒否**し、ロード時 assert で固定している。

## 5. ★ 最重要 — 引き金は cmd `0x34` ではなく**リセットハンドラ**

`bootloader-and-obd-reflash.md` も、本調査の前半も「cmd `0x34` が `0x8000` へ飛ぶ」としていた。
**誤りである。** cmd `0x34` のハンドラ (`0x1B44`) は `0x1BDC` の `movem/rts` で終わり、
**どこへも飛ばない** (`0xFFD168 = 0x36` を書き、マジックを照合するだけ)。

`0x1BDE` (実際に飛ぶルーチン) の呼び出し元は master イメージ中に 2 か所だけ:

```
0x00256:  jsr $1BDE     <- リセットハンドラ。0x24A で cmpi.l #$5AA556C9, $0000FFFC
0x01C7A:  jsr $1BDE     <- 0xFFD168 == 0x36 を見る遅延ディスパッチャ (約 250 tick)
```

`0x1BDE` の実体:
```
move.w #$2700,sr ; reset ; move.w #$4001,$FFFA38 ; move.w #$100,$FFFB02 ; lea $8000,a0 ; jmp (a0)
```

### 5.1 `0x8000` と `0xFFFC` は RAM ではない

CS 初期化 (`0x3F4`–`0x43C`) の `CSBARBT = 0x0006` は、MC68336/376 UM (p.336, D.2.19–21) の
定義で **ベース `0x000000` / ブロック 512 KiB** = master フラッシュそのもの。
内蔵 RAM は TPURAM と SRAM (`RAMBAH/RAMBAL @0xFFFB44` ← `0x00FFE000`) しかない。

⇒ **`0x8000` は較正セクタ (SA3) の先頭、`0xFFFC` はその最後の 4 バイト。**
DS2 では `0x200000` と `0x207FFC` (master) / `0xA00000` と `0xA07FFC` (slave)。

### 5.2 コミット点はマジックを書いた瞬間

リセットハンドラの経路を正確に書くと:

```
0x212  a2 = 0x4800                    ; AIF のブートモード語を探す
0x21A  bne 0x24A                      ; 先頭が非ゼロなら即マジック照合へ
0x21E  ゼロを読み飛ばして最初の非ゼロ語を探す
0x224  cmpi.w #$FFFF -> 一致なら 0x22A jsr $10400   ; アプリの初期化ルーチン。**rts で戻る**
0x230  cmpi.w #$F500 / 0x236 cmpi.w #$00F5 -> どちらでもなければ
0x24A  cmpi.l #$5AA556C9, $0000FFFC   ; ★ ここ
0x256  jsr $1BDE                      ; 一致したら飛ぶ
```

実車ダンプ (hw2001)・純正 CSL ダンプとも `0x4800` は `00 00 00 00 00 00 00 00 FF FF…` で、
最初の非ゼロ語は `0xFFFF`。したがって `jsr $10400` (アプリ初期化) を経由する。

### ⚠ 経路は確定、復帰は静的読みのみ (2026-09-04 訂正)

**配布イメージと実車では通る経路が違う。** SP-DATEN やフォーラム由来のファイルは SA1 が `0xFF` に
消えているので `0x4800` の語が即座に非ゼロになり、`0x21A` が**マジック照合へ直行する**。実車は
先頭 8 バイトが `00` なので読み飛ばし、`0x4808` の `0xFFFF` を拾って `0x22A: jsr $10400` へ行く。

実車の標準 M3 ダンプと CSL 0401 参照イメージを、それぞれ自分の AIF と相手の AIF で回した 4 通りで
確認した。**プログラムは無関係で、AIF だけが分岐を決める。**

`resetHandler.test.ts` は**配布イメージでしか走っていなかった**ため、実車が通る長い方の経路は
**一度も実行されていない**。エミュレータでその経路を回すと、2 億命令走らせても `jsr $10400` から
戻らない。

**これはエミュレータの限界であって、実車がハングするという主張ではない。** 静的には戻る:

- `0x10400` — VBR 設定、`SYNCR`/`SYPCR` 設定、カウンタ付き PLL 待ち (`0x276` 回)、`jsr $106CE`、
  最後は `0x104FC: move.l (a7)+,d2` / `0x104FE: rts`。
- `0x106CE` — `movem.l d2/a2,-(a7)` で始まり、SIM レジスタから RAM 長を `0xFF6` か `0xFD0` に決め、
  `>>2` した約 1012 ロングワードを埋めて検証し、`0x1076A: movem.l (a7)+,d2/a2` / `0x1076E: rts`。
  **ループはすべてカウンタ付き。**

本エミュレータが検証されたのは BMW の**フラッシュスタブ** (`bmwStubs.test.ts`) — 小さく自己完結した
ルーチン — によってであり、アプリ起動初期化はその守備範囲の外。`RAMBAH`/`RAMMCR` を書いてから
4 KiB モデルに対して RAM をサイジングし、本モデルが実装していない SIM レジスタを読む。観測される
のは 1 命令でのハングではなくルーチンの再実行で、これは RAM 検証失敗が生む挙動と一致する。

### ✅ 決着 — `0x24A` は通常起動の経路上にある

エミュレーションは不要だった。BL の当該区間を読めば済む:

```
0x0022A: jsr    $10400            ; 実車 AIF はここを通る
0x00230: cmpi.w #$f500,(a2)       ; jsr から戻るとここに落ちる
0x00234: beq.b  $23e
0x00236: cmpi.w #$00f5,(a2)
0x0023A: bne.w  $24a              ; (a2)=0xFFFF なのでマジック照合へ
0x0024A: cmpi.l #$5aa556c9,$fffc  ; ★
0x00254: bne.b  $25c              ; マジック無し -> 通常起動へ続く
0x00256: jsr    $1bde             ; マジック有り -> ローダへ
0x0025C: lea.l  $ffe500,a0        ; 通常起動の続き
```

`jsr $10400` の戻り先は `0x230` で、そこから `0x23A` の `bne.w $24a` を経てマジック照合に落ちる。
**この区間はマジックの有無と無関係に毎回実行される。** arm が変えるのは `0x24A` の比較結果だけで、
経路そのものではない。

⇒ **実車が始動するたびに、この経路は `jsr $10400` を呼び、戻り、`0x24A` に到達している。**
戻らなければエンジンは掛からない。到達性はエミュレータより強い根拠で確定した。

`resetHandler.test.ts` の最後の 1 件はハーネスの限界を固定するために残してあるが、**安全上の
未決事項ではない**。

照合は **BL がアプリへハンドオフする前**、K-line が使える状態になる前に走る。

> **フラッシュ `0xFFFC` にマジック `5A A5 56 C9` を書いた瞬間から、
> その DME は電源投入のたびに必ず `0x8000` へ飛ぶ。**
> ローダが停止・暴走・CS 設定ミスのいずれかで失敗すれば、
> **ECU は二度と DS2 に応答せず、OBD からは解除できない** (OBD 自体が初期化されない)。
> **SA0 を 1 バイトも消していなくても、BDM 以外に復旧手段が無い。**

### 5.3 だから設計を反転させる

**ローダの最初のフラッシュ操作は、マジックの消去でなければならない。**
`0xFFFC` に `00 00 00 00` を書く (1→0 のみ。消去不要)。これが成功して初めて SA0 へ進む。

これが買うもの (**過大評価しないこと**):

1. **armed の窓が最短になる。** 「setup + 消去 + 16 KiB 書込 + 照合」の全区間から、
   **setup 区間だけ**に縮む。マジックを消した後の失敗は、もう「毎回ローダに落ちる」型の
   ブリックにはならない。
2. **最小コストの自己診断。** 4 バイトの書込が、CS 設定・RAM スタブ・ウォッチドッグ・
   AMD コマンド列という **16 KiB の作業が必要とする機構すべて**を実機上で証明する。
3. **「armed のまま無限再試行」の罠が消える。** 照合失敗時に再試行しても、
   マジックは既に無いので電源を切れば正常起動に戻れる。

**買わないもの (重要):** ローダが**そもそもフラッシュに書けない**場合
(CS 設定ミス・RAM 未初期化・スタック未設定) は、マジックも消せないので**ブリックのままである**。
順序の入れ替えはこの失敗を救わない。

⇒ その失敗を潰すのは順序ではなく、次の 2 つ:
- **オフラインのエミュレータ検証** (CPU32 コア + Am29F400B 状態機械モデル)
- **プローブローダ** (§5.5)

### 5.4 ⚠ ローダを走らせる方法は arm しかない

cmd `0x34` 経由の遅延ディスパッチャ (`0x1C7A`) も、ハンドラ `0x1B44` が先に
`0xFFFC` のマジックを照合し、不一致なら `0xFFD168` を `0x1BD6` でクリアする。
⇒ **リセット経路でも cmd `0x34` 経路でも、マジックが無ければローダは走らない。**
「安全に予行演習してから arm する」はできない。**最初の arm が最初の実行である。**

### 5.5 だから最初の arm は「プローブローダ」にする

最初に書き込むローダは、**SA0 に一切触れないもの**にする:

```
setup (SSP / VBR / RAM / CS / ウォッチドッグ / RAM スタブ)
  -> 0xFFFC に 00 00 00 00 を書く
  -> 読み戻して確認
  -> 停止 (電源を切ってもらう)
```

**最小の実行可能ローダであり、同時に自分を無効化する。**
これが成功すれば「この個体でローダの機械設定が正しい」ことが実証され、
しかも ECU は既に disarmed になっている。失敗すればブリックだが、
**失敗しうる範囲は setup だけ**に限定されており、そこはエミュレータで潰せる。

プローブが通って初めて、SA0 を置換する本番ローダを arm する。

### 5.6 片方ずつ arm する (両 CPU 同時は禁止)

引き金がリセットハンドラなので、**cmd `0x34` で両 CPU を同時に起動する必要はない**。
slave にも同一のリセットフックがある (`0x80258: jsr $1BDE`、タグ `0x3FE0` = `"SS"`)。

⇒ **arm したい側の較正セクタにだけマジックを書き、電源を入れ直す。**
slave を arm すれば **master は正常起動して DS2 を生かしたまま** slave のローダが走る。
結果を観測でき、失敗しても master は生きている。**両方同時に賭けるより厳密に優れている。**

なお master 側の cmd `0x34` は成功経路で**応答コードを書かない** (`0xB0` の拒否経路だけが書く)。
「受理された」と「何もしなかった」は区別できない。

## 6. `reset` 命令の後、機械はほぼ初期状態

MC68376 UM Table 5-14: `RESET` 命令は **MSTRST + EXTRST** を出す。CPU は保たれるが
**オンチップの他モジュールはリセットされる**。既定値 (UM Table 5-21/5-22, App. D):

- `CSOR[0:10]`: BYTE = Disabled、R/W = Disabled
- `CSBAR[0:10]`: base `0x000000`、ブロック **2 KB**
- `CSORBT`: 1 MB @ 0、両バイト、**Read/Write**、13 wait
- `TRAMBAR` / SRAM: 配列 **無効**
- ポート DDR: すべて入力

⇒ 常駐ルーチン `0x31C0` の 4 本のレジスタ書込を**コピーするだけでは足りない**
(あれは初期化済みの機械で走り、前値を保存・復元している)。
ローダは `CSPAR0/1`・`CSBAR*`・`CSOR*`・RAM・ポート方向を**自分で全部作る**必要がある。

> 救い: `CSORBT` の既定値は 1 MB @ 0 / Read-Write / 13 wait なので、
> **既定値のままでもフラッシュの読みと書きは通る**。最も安全な選択肢はこれ。

`0xFFFA38` = **CREG (SIM テストサブモジュール制御)**、`0xFFFB02` = **TRAMTST (TPURAM テスト)**。
どちらも UM App. D で **"factory test only"**、ビット定義は非公開。
チップセレクトにもメモリマップにも属さないので `jmp $8000` の着地点は変えないが、
**実際の効果は文書化されていない**。実機でしか確定しない。

### 常駐ファームの書込許可

`flash_command_dispatch` (`0x31B6`) はフラッシュ操作の前後で CS を切り替える:

| | 通常時 | フラッシュ操作中 |
|---|---|---|
| `CSORBT` (0x000000+512K) | `0x7830` = R/W 両方 / 0 wait | `0x68F0` = **読出専用** / **3 wait** |
| `CSOR0` (同一範囲) | `0x6030` = R/W `00` = 不活性 | `0x70F0` = **書込専用** / **3 wait** |

同じ 512 KiB に 2 本の CS を重ね、**読みは CSBOOT・書きは CS0** に分け、
さらに**ウェイトを 3 に落として**書込パルス幅を確保している。
単に書込を許可するだけでなく**タイミングも変えている**。

## 7. ローダの必須要件

68k (CPU32)。SA3 (32 KiB) に「ローダコード + 新 BL 16 KiB + マジック」を収める
(`blLoader.ts` が組立と検証を担う)。**BMW 常駐ルーチンを推測で作り直さず逐語的に複製する**のが原則。

1. **先頭バイト** ≠ `0x01`(master) / `0x02`(slave)。リセット経路と cmd `0x34` の両方が
   `(*(u32*)0x8000)>>24` を見る。較正イメージは master `01 0E…` / slave `02…` で始まるので、
   この門は「有効な較正を実行してしまう」ことを防ぐためにある。
   ⇒ `move.w #$2700,sr` (`46 FC…`) か `bra.w` (`60 xx`) で始める。
2. **SSP と VBR を最初に設定**。リセット経路では `A7 = 0` (TPU レジスタ領域を指す)。
   **RAM に自前スタックと、全ベクタを安全な無限ループに向けたベクタ表を作り `VBR` を移す**。
   既定 `VBR=0` のままだと、SA0 消去後の**あらゆる例外が消去済み領域のベクタを踏んで即死**する
   (IRQ7・バスエラー・アドレスエラーは `sr=0x2700` でもマスクできない)。
3. **RAM を自分で有効化**。`reset` 直後は SRAM も TPURAM も無効。
4. **チップセレクトを自分で完全設定** (§6)。ポート方向も。
5. **ウォッチドッグ**。`SWSR($FFFA27)` に `0x55`→`0xAA` を**全ポーリングループ内**で叩く
   (16 KiB 消去は約 1 秒)。`reset` が `SYPCR($FFFA21)` の write-once 窓を開け直すので、
   **SWE を落として無効化**するのが安全。
6. **フラッシュスタブは RAM 常駐**。Am29F400 は単一バンクで read-while-write 不可 —
   消去/書込中はチップ全体が読めず、命令フェッチも status を返す。
   16 KiB の像は RAM (合計 7.5 KiB) に載らないので、**SA3 に置いたまま
   1 ワードずつ「書込パルスの前」(チップが read モードのとき) に読む**。
7. **書込は read-modify で複製**。BMW `0x348E`/`0x36E2` は書かない側の半ワードに `0xFF` を入れず、
   **現在値を読んで AND する**。非消去域での `0xFF` 書込は 0→1 違反になり DQ5 abort に落ちる。
8. **ポーリングはワード読み・低位バイト判定・DQ5 後に DQ7 再読み** (BMW `0x360A`–`0x362C`)。
   偶数アドレスでバイト読みすると DQ15–8 を見て**偽陽性**になる。
   `0xF0` (read-array) は `reset` 命令の後・操作の前に必ず 1 度発行する。
9. **★ 最初の書込 = `0xFFFC` へ `00 00 00 00`** (§5.3)。
10. 消去 → 16 KiB 書込 → **読み戻し全バイト照合 + CRC 照合**。失敗時は再試行。
    `reset` は成功経路にのみ現れる。
11. **staged セクタを書くときマジックは必ず最後尾**。`stagedWriteOrder()` が
    「マジックを**完成させる**チャンク」を最後に置くことを assert する
    (小さいチャンクではマジックが 2 チャンクに跨るが、不完全なマジックは一致しないので安全)。

## 8. 危険と復旧

| 段階 | 失敗時 | BDM 無しで戻せるか |
|---|---|---|
| フルバックアップ (読み出しのみ) | 何も起きない | — |
| プログラム域での予行演習 | プログラムが壊れる | **戻せる** |
| staged セクタ書込 (マジック**前**) | 較正が壊れているだけ | **戻せる** |
| **マジックを書いた瞬間〜ローダがマジックを消すまで** | **毎回 `0x8000` に飛ぶ。DS2 応答なし** | **戻せない** |
| ローダがマジックを消した後〜SA0 書込完了まで | リセットベクタ喪失 | **戻せない** |
| SA0 照合 OK 以降 | 較正/プログラムが空 | 戻せる |

**電源**: 13.5 V の安定化電源 (トリクル充電器は不可)。エンジン停止・クランキング禁止。
消去命令を出した後は**中断する手段が無い**。
`0x1BDE` の `reset` はポートモジュールもリセットするため、
**メインリレーをポートで保持している場合、ECU が自分の電源を切る可能性**がある。要回路確認。

**フラッシュカウンタ**: CPU あたり **30 スロット**、1 セッションで 1 消費。
開発で何度も staging すると枯渇し、回復には SA1 の消去・再書込が要る。
**SA1 は失うと復旧不能。ハード資源として予算管理する。**

**フラッシュ品種**: ✅ **確定** (2026-09-04)。ファーム自身は autoselect (`0x90`) を発行しないので
ファームからは確定できないが、**YulCmr の BDM ツールが `Read EEPROM ID` で電気的に読んでおり、
HP では AM29F400 を表示する**と `step_by_step_guide.mkd` が明記している。刻印を読むより強い
裏付けであり、セクタ地図とタイミングの前提はこれに乗ってよい。
一次資料は YulCmr リポジトリの `docs/am29F400B_doc.pdf` と同 `step_by_step_guide.mkd`。

**EEPROM ロックは存在しない。** YulCmr のガイドは AM29F400 / AM29F200 を "EEPROM" と呼んでいるが、
これは NOR フラッシュそのもので、別体の EEPROM は無い。同ガイドに protection byte / security /
locked の記述は一切無い。

Am29F400B にはハードウェアのセクタ保護機能自体はある (A9 高電圧で設定、車載では変更不可) が、
**SA0 は保護されていない**。根拠は同じガイドで、BDM の手順は `Erase Memory` → `Write Memory` で
あり、その目的がまさに `21132300` → `21132500` = **SA0 の書き換え**である。成立している以上、
SA0 にハードウェア保護は掛かっていない。

⇒ OBD で SA0 を消せない理由は**ファームの許可ニブル一覧 (§4) だけ**であり、ハードの制約ではない。
ローダを SA3 で走らせる設計は、その門を通らずに済ませるためのものである。

**EWS alignment**: YulCmr のガイドに EWS 整合の節があるのは、BDM がドナーのバイナリを丸ごと
書くからである。**本ツールは SA1 (VIN・AIF・フラッシュカウンタ) に一切触れない**ので、この工程は
原理的に不要なはず。ただし **EWS のデータが SA1 のどこにあるかは未確認**なので、「不要なはず」
までしか言えない。実車バックアップを取った際に確定させること。

## 9. オフライン検証ハーネス — 実装済み

`packages/dme-flash/src/emulator/` に、実機に触れずにローダを完走させる仕組みがある。

| ファイル | 役割 |
|---|---|
| `flashAm29f400.ts` | Am29F400BB の状態機械。セクタ地図・AMD コマンド列・DQ7/DQ5・**書込はビットを 0 にしかできない**・**動作中はチップ全体が読めない** |
| `cpu32.ts` | CPU32 インタプリタ。**未実装オペコードは例外を投げる**(黙って飛ばさない) |
| `machine.ts` | メモリマップ・SIM レジスタ・チップセレクト・RAM 有効化・ウォッチドッグ |
| `asm68k.ts` | CPU32 ミニアセンブラ (式評価・`equ`・2 パス)。**理解できない記述はエラー** |

### 検証は「自分の理解」ではなく「既知の正解」で行う

各層を、BMW 自身のコードで検証している:

- **アセンブラ** — BMW の `flash_erase_sector` を本アセンブラの構文で書き、
  `0x35DA` の 0x62 バイトと**バイト単位で一致**することを確認 (`asm68k.test.ts`)。
- **エミュレータ** — BMW の消去/書込スタブ 2 本をイメージからそのまま取り出して実行
  (`bmwStubs.test.ts`)。実車で動くコードが正しくモデルを駆動できるなら、モデルは代役として信用できる。

**この方針が実バグを 5 件捕まえた。** 自分でテストを書いていたら同じ誤解を共有して通っていたもの:

1. CPU の MOVE 判定が `(op >>> 12) & 3` で、`eor.w` (`0xB342`) が MOVE として実行されていた。
2. 実効アドレスの `(mode, reg)` を **6 箇所で逆に渡していた**。BMW のスタブは `lea`/`jsr` を
   使わないので露見せず、`tst.b d2` は偶然同じ値を読んで正解に見えていた。
3. フラッシュモデルが「中断した操作」を busy のままにしていた。実機では DQ5 が立った時点で
   操作は停止しリセットコマンドを受け付ける。この誤りだと失敗後に二度と命令をフェッチできない。
4. `CSORBT` のリセット値を誤っていた (正: `0x7B70` = **R/W 両方**)。§6 の結論が変わる。
5. プローブローダのコピーループがウォッチドッグを叩いていなかった
   (`SYPCR` の最短タイムアウトは約 25 µs)。

## 10. ローダ — 実装済み・オフライン検証済み

### 10.1 プローブローダ (`tools/loader/probe.s`、200 バイト)

**最初に arm する唯一のもの。SA0 に一切触れない。**

```
SR マスク → SYPCR 最長タイムアウト → SRAM 有効化 → 自前スタック
  → スタブを RAM へコピー (ループ内でウォッチドッグ)
  → ★ 0xFFFC に 0 を書く (= 自分を無効化)
  → 読み戻し確認 → 停止
```

意図的にやらないこと 2 つ:
- **チップセレクトに触れない** — リセット値 `0x7B70` で既に読み書き可 (§6)。
  「arm したのに書込が黙って捨てられる」という最有力の失敗要因を丸ごと消す。
- **ウォッチドッグを止めない** — ハングしてもリセットで正常起動に戻れる。
  マジックの消去は途中で中断されても安全 (不完全なマジックは一致しない)。

`probeLoader.test.ts` (16 tests) が、`reset` 直後の実際の状態から完走することと、
**注入した各危険で必ず失敗すること**を固定している。

### 10.2 置換ローダ (`tools/loader/replace.s`、530 バイト)

```
1 機械設定  2 VBR を RAM のベクタ表へ  3 スタブを RAM へ
4 ★マジック消去 (disarm)  5 staged イメージの健全性検査
6 SA0 消去  7 16 KiB 書込  8 照合、不一致なら 6 へ再試行 (3 回)
9 停止 → ウォッチドッグ → 新 BL で起動
```

**順序の理由**:
- **4 が 5 より前** — イメージ不良で拒否したとき、マジックが残っていると
  電源投入のたびにローダへ落ちる (BL は無傷なのに BDM 必須)。先に disarm すれば正常起動に戻る。
- **2 が 6 より前** — 例外ベクタは番地 0 = SA0 にある。消去後に例外が起きると
  `0xFFFFFFFF` をベクタとして読み double bus fault → CPU 停止。IRQ7・バスエラー・
  アドレスエラーは `sr=0x2700` でもマスクできない。RAM のベクタ表に逃がしておく。
- **5 の中身** — MSS54 の BL はリセットベクタの初期 PC が必ず `0x00000200`。
  staged イメージが空なら `0xFFFFFFFF` になるので、**SA0 を消す前に**気づける。3 命令で済む。

`replaceLoader.test.ts` (19 tests) の要点:

- **実車の標準 M3 ダンプ (`hw2001`) から出発し、純正 CSL SA0 とバイト一致で終わる。**
  終了後の SA0 は `identifyBootloader` = `csl`、CRC = `0x3C45`、型番 `"21132500"` ×3。
- SA0 とマジック以外はフラッシュのどこも変わらない。**SA1/SA2 (VIN・AIF・フラッシュカウンタ) は無傷。**
- 消去確認サイクルの瞬間に `VBR == 0x00FFE000` であることを動的に検証。
  さらに `movec` を NOP に潰した対照実験で、その検証が実際に効いていることを示している。
- staged イメージが空なら **SA0 を消さずに拒否**し、しかも disarm 済み。
- 書けないセル / 消えないセクタでは**ハングせず**諦める。

### 10.3 危険な窓の実時間

Am29F400B のデータシート値から:

| 操作 | 標準 | 最悪 |
|---|---|---|
| SA0 (16 KiB) セクタ消去 | 約 0.7 s | 約 15 s |
| 8192 ワード書込 (7 µs / 300 µs per word) | 約 0.06 s | 約 2.5 s |
| **合計 (消去開始〜照合完了)** | **約 1 秒** | **約 18 秒** |

この間 OBD 通信は一切発生しない。残る失敗要因は**電源断とチップ故障だけ**。
⇒ 13.5 V の安定化電源が要件である理由がこれ。トリクル充電器は不可。
