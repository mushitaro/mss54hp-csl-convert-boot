# ブートローダとは何か / OBD でブートローダを書き換える経路 — 実測

> ## ⚠ 本書には誤りがある — [`bootloader-replacement.md`](bootloader-replacement.md) を先に読むこと
>
> 後の実測で、本書の中核 3 点が誤りと判明した。**本書の手順どおりに実行してはならない。**
>
> 1. **cmd `0x06` は「メモリ書込」ではなく「メモリ読み出し」** (ハンドラ `0x1F44`、
>    ループ `0x201A` は `move.b (a0),(a2)`)。§4.1 の「RAM に任意コードを書ける」は成立しない。
>    そのまま実行すると、フラッシュ配列に生の store を撃つことになる。
> 2. **`0x8000` と `0xFFFC` は RAM ではなく較正セクタ (SA3)**。`CSBARBT = 0x0006` は
>    ベース `0x000000` / ブロック 512 KiB = master フラッシュそのもの。
>    エンコードも `0cb9 5aa5 56c9 0000 fffc` (絶対ロング `0x0000FFFC`) と
>    `41f9 0000 8000` (絶対ロング) で、region_table の RAM 窓 (`0xFF8000`/`0xFFD000`) とは別物。
> 3. **cmd `0x34` は跳ばない**。ハンドラ `0x1B44` は `0x1BDC` の `rts` で終わる。
>    実際に飛ぶ `0x1BDE` の呼び出し元は**リセットハンドラ `0x256`** と遅延ディスパッチャ `0x1C7A`。
>    ⇒ **後戻り不能点は「マジックを `0xFFFC` に書いた瞬間」**であり、cmd `0x34` の送信ではない。
>
> また §5 の「RAM ローダのバイナリが未入手だから実装できない」という結論は**撤回する**。
> ローダは較正セクタに置くもので、その経路は実車実証済みである。
> なお §4.3 の「master は `0x01…` で始まる健全なコードか」も**逆**で、
> `0x01` で始まるものを master は**拒否**する (有効な較正を実行しないための門)。


このプロジェクトの核心。すべて DME ファーム (`data/211325000401PD31_Community_Patch_v1.bin`、
あなたの DME と同族の 211323 CP v1 でも同一) の逆アセンブルと、コミュニティ資料
(`github.com/YulCmr/MSS54_HP_CSL_Clone_info_gathering`) の突き合わせで確定した。

## 1. ブートローダとは

**電源投入時に最初に走り、フラッシュの残りを書き換えられる唯一の存在。**

- リセットベクタ (master 先頭 8 バイト): 初期 PC = **`0x00000200`** → `bootloader_entry`。
- なぜ独立が必要か: **自分が実行しているコードは消せない**。NOR フラッシュは消去/書込中に読めない。
  ファームは各フラッシュ操作を `_ramstub` (自分を RAM にコピーして RAM 上で実行) にして
  この制約を回避している。
- 配置 (各 CPU 512 KiB の先頭側): `0x0000`–`0x3800` BL 本体 / `0x4000`–`0x6000` Free Identifiers
  (VIN・AIF・フラッシュカウンタ) / `0x6000`–`0x7FFF` ガード / `0x10000`– アプリ。
- 起動判断 `boot_handoff_dispatch` (master `0x30BE`): `aif_tail_guard_key == 0x66` ならアプリへ
  ジャンプ、さもなくば BL に留まりプログラミングを待つ。
- **OBD の消去/書込テレグラムを受け取って実行しているのが、この BL のコード。**
  `region_table` も `flash_req_parse` も NOR コマンド列も、全部 BL の一部。

## 2. M3 BL (`21132300`) と CSL BL (`21132500`) の違い — 実測

CP v1 の両版 (1 MiB) の差は **25 バイトのみ**。BL 領域に限れば **6 バイト**:

- 識別子 ASCII `'3'`↔`'5'` (`0x03FD7/DF/E7`) とその 16bit チェックサム。
- **命令 1 個** (`0x012AE`): `TST.B $0008E002` (M3) ↔ `TST.B $0008F002` (CSL)。
  BL がアプリ較正から 1 バイト読んで健全性を見ており、読む先が違う。M3 BL は `0xE002` を見るが
  そこは `K_FR_T_ADAPT` と重なるため、CP v1 の M3 版は `0xE002 = 0x0100` にする (#5)。

⇒ **BL は「仕組みの違い」ではなく、フラッシュの版と、健全性チェックの参照先が違うだけ。**
コード・フラッシュ方式は同一。

## 3. コミュニティの BDM 変換 (`YulCmr`)

**BDM = MC68336 の Background Debug Mode。ハードウェア。ECU を開けてリボンケーブルを挿す。**

- 5 線 (`BKPT`/`FREEZE`/`RESET`/`DSI`/`DSO`) を STM32 で叩き、CPU を停止させて外からフラッシュを
  直接読み書きする。「erase and write twice, once per side, Master & Slave」。
- **CPU が止まっているので「自分を消せない」問題が起きない** → **BL 領域を含む全フラッシュを書ける**
  → `21132300 → 21132500` が可能。
- これは **OBD ではない**。terra/MPowerE36 が「ブートローダで」と言うときの一部はこれ (外部 BDM)。

`YulCmr` は本プロジェクトの独立検証にもなった:
- VANOS: `0x1802: 00 1E→FF EC` (+3.0→−2.0)、`0x1BB6: FF EC→00 0A` (−2.0→+1.0)、
  「**stock cams のとき適用。CSL cams なら不要**」。本ツールの実測と一致。
- フラッシュチップ = **Am29F400BB** ×2 (各 512 KiB)。CPU クロックはソフトで 20/25 MHz 切替。

## 4. ★ OBD でブートローダを書き換える経路 — ECU に実装されている

**私は当初「OBD で BL は書けない」と断定した。誤りだった。撤回する。**
正しくは「**走行中の BL では書けないが、RAM ローダに逃げれば書ける。その入口は ECU に実在する。**」

### 4.1 RAM ローダを送り込む口 — `region_table` の無制限セグメント

`flash_req_parse` (master `0x289C`) は `req[4..6]` から 24bit アドレスを作り、`region_table` の
エントリで受理判定する。全 65 エントリを読むと、**フラッシュ窓 (nibble) 以外に直接アドレスの
エントリがある**:

| セグメント id | 範囲 | 中身 |
|---|---|---|
| **`0x05` / `0x0C`** | **`0x000000`–`0x1000000`** | **全 16 MB = 制限なし。RAM を含め何でも** |
| `0x01` / `0x08` | `0xFF8000`–`0xFF9000` | 内蔵 RAM |
| `0x04` / `0x0B` | `0xFFD000`–`0xFFF000` | 内蔵 RAM (診断バッファ) |
| `0x0E` | `0x424150`–`0x424160` | recycling |
| `0x03` / `0x0A` | `end<=start` | **ガードセクタ = 構造上到達不能** |

⇒ **cmd `0x06` (メモリ書込) をセグメント `0x05` で使えば、RAM (`0x8000`, `0xFFFC`) に任意コードを
書ける。** cmd 0x06 ハンドラ (`0x1F44`) はセグメント値で分岐し、`0x201A` で解決アドレスへ直接ストアする。

### 4.2 RAM ローダへ実行を移す口 — cmd `0x34`

cmd `0x34` ハンドラ (`0x1B44`) を完全に読んだ:

```
move.b  #$36, ($ffd168)          ; プログラミングモード進入マーク
cmpi.l  #$5AA556C9, ($fffc)      ; ★ RAM 0xFFFC のマジック鍵を照合。無ければ 0xB0 で拒否
move.l  (a4=$8000), d0           ; RAM 0x8000 の先頭を検査
andi.l  #$ff000000, d0
cmpi.l  #$01000000, d0           ; master は 0x01… で始まる健全なコードか
...
move.w  #$2700, sr               ; 割り込み全禁止
reset                            ; 周辺リセット
lea     $8000, a0
jmp     (a0)                     ; ★ RAM 0x8000 のコードへジャンプ
```

- **マジック `0x5AA556C9` を RAM `0xFFFC` に置き、RAM ローダを `0x8000` に置いて、cmd 0x34 で飛ぶ。**
- reset→jump の実体 (`0x1BDE`) はリセットハンドラ (`0x256`) からも参照 = 起動シーケンスと共有。
- **あなたの DME (211323 CP v1) でも cmd 0x34・マジック・ジャンプはバイト単位で同一** (BL 領域の差は
  `0x12AE` の 1 バイトのみ)。コマンドテーブル (`0x37A2`, 12 コマンド) も完全一致。

### 4.3 手順 (機構として成立する筋)

```
1. login / access (cmd 0x91 = 固定パスワード, security-access-cmd90-91.md)  — アクセスレベル確保
2. cmd 0x06 seg 0x05 → RAM 0x8000 に RAM ローダ本体を書く (≤128B/回)
3. cmd 0x06 seg 0x05 → RAM 0xFFFC に 5A A5 56 C9 を書く
4. cmd 0x34 → マジック照合 → RAM 0x8000 へジャンプ
5. RAM ローダが、ホスト (OBD) と自前プロトコルで対話しながら
   BL セクタを含む全フラッシュを消去・書込 (フラッシュから命令を取らないので可能)
6. reset → 新 BL で起動
```

**OBD は通信経路。バックアップとイメージはホスト側。消去/書込は RAM ローダが実行。**
= あなたの読みどおり。ToolSet32/WinKFP の `10flash.prg` (REVISION 2.15, "Spezial SGBD nur zum
flashen") はこの送り側で、KWP2000 プログラミング SID (`ERROR_ECU_CANNOT_DOWNLOAD_TO_SPECIFIED_ADDRESS`
等) と `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN` (seed) を持つ。

## 5. まだ確定していない (推測で埋めない)

RAM ローダへ「送り込んで飛ぶ」までは ECU 側で確定した。**その先 = RAM ローダ本体は ECU に無い。
ホスト (WinKFP/MPowerE36) が送り込むもの**であり、手元に無い。確定に要るのは:

1. **RAM ローダのバイナリ** — WinKFP が送るもの、または自作。これが無いと 4.3 の 5 が空。
2. **cmd 0x06/0x34 の正確なテレグラム列** — `10flash.prg` の BEST バイトコードから、または実車の
   WinKFP 通信ログから。job 名は採れたが、生バイトは BEST 逆アセンブルが要る。
3. ~~**login (seed-key) アルゴリズム** — cmd 0x90/0x91。~~ **確定 →**
   [`security-access-cmd90-91.md`](security-access-cmd90-91.md)。実体は **seed-key ではなく固定
   パスワード**(`0x3FB8` の `00 25 80`/`00 96 00`/`01 E8 48` → レベル 2/6/8 を直接照合)。ただし
   WinKFP が使う KWP2000 `$31/07-08` auth は DS2 コマンド表の**外の別レイヤ**で、そちらの seed-key
   有無は未確定。
4. **RAM ローダとホストのプロトコル** — どうアドレス/データを渡すか。

さらに **BL を書く行為はこのプロジェクト最大の危険** — 失敗すれば BDM でしか戻せない。
RAM ローダの正しさは、送り込む前にオフラインで完全に検証する必要がある。

## 6. 結論

- **論理的・機構的には、OBD だけで BL を含む全フラッシュを書ける** (cmd 0x06 seg 0x05 + cmd 0x34)。
  ECU 側の受け口は全て実在し、あなたの DME でも同一であることを確認した。
- ただし **送り側 (RAM ローダ + プロトコル + seed-key) が未入手**で、そこが空のままでは実装できない。
- **実車での実証例は未確認。** コミュニティで観測できるのは BDM (ハード) の変換。OBD で BL を書く
  MPowerE36 系は YouTube のみで、スクリプト実体は未入手。
