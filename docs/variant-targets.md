# 変種 (MAP / フラップ) の対象 — 実測

UI の 3 択が実際にどのバイトを触るのか。アドレスはすべて **64 KiB 較正ペア (partial BIN) のオフセット**
(`0x0000`–`0x7FFF` = slave / `0x8000`–`0xFFFF` = master)。値は**純正 CSL 較正 `A7837331.0DA` (PD31) から実読**。

## 結論 — 変種はすべて較正だけで作れる

| | MAP 系 | フラップ (ASK) 系 |
|---|---|---|
| 定数 | **すべて master 半分** | **すべて slave 半分** |
| DTC | `DTC_DF_MAP_PRESSURE` @`0xF420` (master) | 3 件すべて slave |
| プログラム域の変更 | **不要** | **不要** |

**これが本プロジェクトで最も重要な発見。** 変種はプログラム 512 KiB を一切変えないので:

- プログラムは **BMW が配布したまま**書ける。
- したがってプログラム側の整合フィールド — DS2 selection `0x0C` で報告される
  `DAT_00041be0` (DS2 `0x531BE0`) の 16bit 値を含む — は**構成上そのまま正しい**。
  **アルゴリズムを同定する必要が無い** (未同定のままでよい)。
- 再計算が要るのは**較正の CRC-16/ARC だけ**で、これは既知・実装済み・純正ファイルで検証済み。

当初計画の「純正 SP-DATEN 橋渡し」は、**プログラムについては文字どおり成立する**。

## MAP センサー (master 半分)

`k_rf_cfg` @ **`0xE5E4`**、純正 CSL = **`0x12`** (実読で確認)。ビット構成は
`E46M3CSL_TuningTool/docs/ecu-logic/10-load-path.md` §3:

| 値 | RF 算出 |
|---|---|
| `0x02` | `rf_soll` (Alpha-N + TABG 補正) のみ |
| `0x10` | MAP 積分項 `rf_p_saug_i` を加算 |
| **`0x12`** | **純正 CSL = 両方** |
| `0x01` | MAP 直接 |
| `0x04` | HFM (ハード改造前提・不可) |

**`RF_PT_KORR` (吸気温・大気圧補正) は `k_rf_cfg` では切れない。** `rf_soll_calc` は
`k_rf_cfg` を一度も読まない。3 択のどれを選んでも常に効く。

| 選択 | `k_rf_cfg` | MAP 診断 | 意味 |
|---|---|---|---|
| **使う (純正 CSL)** | `0x12` のまま | そのまま | 無改変。MAP センサー装着が前提 |
| **今は使わない・後で使う** | `0x12` のまま | **抑制** | MAP 経路と較正を残したまま DTC だけ止める。センサーを付けたら診断を戻すだけ |
| **使わない (フル遮断)** | **`0x02`** | 抑制 | 純 Alpha-N。MAP 積分項が VE 誤差を隠さない |

関連定数 (すべて master、純正値は実読):

| シンボル | アドレス | 純正 CSL | 役割 |
|---|---|---|---|
| `k_p_saug_steigung` | `0xD2EE` | `0x9A70` | MAP 変換の傾き |
| `k_p_saug_offset` | `0xD2F0` | `0x0026` | 同オフセット |
| `k_p_saug_diag_min` / `_max` | `0xD2F2` / `0xD2F4` | `0x0C80` / `0x9600` | **MAP 妥当性の下限/上限** |
| `k_p_saug_umg_diff_max_ans` / `_max` | `0xD2F6` / `0xD2F8` | — | 大気圧との差の上限 |
| `k_p_saug_error_min` / `_max` | `0xE08A` / `0xE088` | — | MAP エラー帯 |
| `k_rf_p_saug_i_min` / `_max` | `0xE5EE` / `0xE5F0` | — | 積分ワインドアップ制限 |
| `K_RF_DIAG_SCHWELLE` | `0xE5F8` | — | `rf_diag` ラッチ閾値 |
| `k_rf_diag_d_pwg_max` / `_tau` | `0xE5FC` / `0xE5FE` | — | ペダル変化率ゲート / 再開遅延 |
| `DTC_DF_MAP_PRESSURE` | `0xF420` | 下表 | MAP 圧力の故障コード記録 |

アドレス対応の裏付け: `K_RF_HUBVOLUMEN` @`0xD21C` = **3201** (3.201 dm³)、
`K_RF_LUFTDICHTE` @`0xD21E` = **1136** (1.136 kg/m³) — ドキュメントの記載値と実読が一致。

## フラップ / CSL スノーケル ASK (slave 半分)

### 訂正: 純正 CSL はフラップ加算を**有効**で出荷している

当初の計画は「Karter16 の 0401 イメージは ASK 480 セル全ゼロ・フラップ診断削除済み」としていたが、
**実測はそうではなかった**。純正 PD31 も参照実イメージも、ASK 加算テーブルは**生きている**:

- `kf_rf_soll_ask` Z (480 セル) のうち **188 セルが非ゼロ**
- 負荷とともに単調増加し、全開で **+0.051** (本表 `kf_rf_soll` の最大 1.202 に対し約 4 %)
- 軸は本表と完全に同一 (600–7900 rpm × 0.0–100 %)

TUNER ドキュメントの「480 セル全ゼロ」は**別のイメージ (チューニング済み較正)** を指していた。
実 CSL にはスノーケルフラップがあるので、これが自然。

### テーブル構造 (実測で確定)

| 部位 | アドレス | 長さ |
|---|---|---|
| X 軸 (rpm, 20 点) | `0xDB32` | 40 B |
| Y 軸 (負荷 %, 24 点) | `0xDB5A` | 48 B |
| **Z データ (24×20)** | **`0xDB8A`** | **960 B** |

`0xDB8A + 960 = 0xDF4A` で、次の `kf_rf_soll_tau_up` (`0xDF4C`) と隣接 — 形状の裏付け。

### ASK 定数 (slave、XDF より)

`0x21DA`–`0x21E2` と `0x21FA`–`0x2265` に 31 個。要点:

| シンボル | アドレス |
|---|---|
| `k_ask_zustand_cfg` | `0x21DF` |
| **`k_ask_diag_mode`** | **`0x21E1`** |
| `k_ask_pot_min` / `_tol` | `0x21DE` / `0x21E0` |
| `k_ask_pot_avg_min` / `_max` | `0x21FA` / `0x21FC` |
| `k_ask_flap_diag_tan_min` | `0x2252` |
| `k_ask_flap_driver_*` | `0x21DA`,`0x21DC`,`0x21E2`,`0x2254`–`0x2258`,`0x2263`,`0x2264` |
| `k_ask_diag_min_cycles` | `0x2262` |

| 選択 | 内容 |
|---|---|
| **有り (純正 CSL)** | 無改変 |
| **無し** | ASK 加算 Z を 0 埋め (`0xDB8A`, 960 B) + フラップ 3 DTC を抑制 (+ `k_ask_diag_mode`) |

## DTC レコード — 構造は確定、無効化の符号化は**未確定**

XDF に **241 件**の DTC が 14 バイトのレコードとして定義され、フィールド名も付いている:

```
index:  0    1    2     3       4        5       6      7..11   12    13
        DTC  SIN  SOUT  IN INC  OUT INC  IN DEC  OUT DEC  ...   CTL   TERM
```

純正 CSL PD31 からの実読 (241 件すべて `DTC` がコード名と一致、`TERM=FF`):

| DTC | アドレス | half | 実値 |
|---|---|---|---|
| `DTC_DF_MAP_PRESSURE` | `0xF420` | master | `DF A0 A0 04 01 01 04 00 01 36 17 28 **03** FF` |
| `DTC_7C_CSL_FLAP_POT` | `0x6164` | slave | `7C FA 0A 01 01 01 01 13 14 0A 0B 28 **03** FF` |
| `DTC_1C_CSL_FLAP_REGULATOR` | `0x62DE` | slave | `1C 0A 28 01 01 01 01 13 14 0A 0B 28 **03** FF` |
| `DTC_12_CSL_FLAP_DRIVER` | `0x62EC` | slave | `12 28 28 01 01 01 01 03 0A 0B 14 28 **01** FF` |

`CTL` の分布 (241 件): `0x00`×81, `0x01`×49, `0x02`×11, `0x03`×15, `0x09`×11, `0x23`×2,
`0x25`×23, `0x27`×22, `0x2D`×9, `0x34`×2, `0xA5`×16。**単純な有効/無効フラグではない。**

> **⚠ 無効化の符号化は同定できていない。** `SIN`/`SOUT` はデバウンス閾値、`IN/OUT INC/DEC` は
> その増減量に見えるので「`SIN` を最大にすればラッチしない」は**もっともらしいが未検証**。
> TUNER 側も CTL を「符号」として読むだけで DTC を無効化しておらず (`60-tuning-logic.md` は
> `DTC_24_TANK_VENT_VALVE` の CTL `0x27` を「開かないバルブの符号」と記述し、パッチは
> **戻すこと**と警告している)、この経路は誰も確定していない。
>
> 確定手段は 2 つ: ① DTC エンジン (デバウンス処理) を逆アセンブルで読む、
> ② DTC を止めた既知の較正イメージを入手して差分を取る。
> **どちらかが済むまで「DTC オフ」は UI に出さない。**
