# FAST ENTRY — 125000 baud への入口と、その代償

TUNER (`E46M3CSL_TuningTool`) の高速化実装を読み、本ツールに取り込んだ結果と、
**取り込まなかった一点**の記録。

## 1. 機構

DME は **cmd `0x91` によるボーレート変更を、プログラミングセッションの内側でしか受け付けない**。
そしてブートローダがそのセッションへ入れてくれる唯一の入口は**正当な消去**である。

karter16 の着眼 (journal #385) は、**その消去は「どうでもいい場所」でよい**という点にある。
Free Identifiers セクタ (`0x4000`–`0x5FFF`) はちょうど Am29F400 の 8 KiB 消去ブロック 1 個 —
デバイス上でモードを立ち上げられる最小の単位 — なので、

1. 中身を実機から**生で**読み、
2. そのセクタを消去し、
3. 読んだものを**そのまま書き戻し**、
4. バイト単位で照合してから、
5. `0x91` で 125000 に上げる。

TUNER の実装は `src/lib/dme-link/fastEntry.ts` (純粋な保全計画) と
`webSerialDmeLink.ts:911 enterFastReadMode()` (実行) に分かれている。

### 2 つのブーストは別物

| | FAST READ | FAST WRITE |
|---|---|---|
| セッションを開ける消去 | Free Identifiers (8 KiB) を消して戻す | 目的のデータ域の消去そのもの |
| `0x91` を打つ瞬間 | **全部戻して照合し終えた後** | **データ域が消えたまま** |
| 切替失敗の代償 | 速度だけ | フラッシュ全体 |

TUNER のコメントが「消す量は多いのに **FAST READ の方が安全**」と言うのはこの順序のこと。

## 2. 本ツールが TUNER より厳しくしている点

消すセクタは、**このプロジェクトが守るために存在するセクタそのもの**である。
`imageLayout.ts` の `PROTECTED_IMAGE_RANGES` は `0x4000`–`0x7FFF` を
「絶対に消去・書込しない範囲」と宣言している。VIN・AIF・フラッシュカウンタ・
アプリケーション entry vector が入っており、**配布されているどのフルバイナリにもこの部分は無い**
(全て 0xFF に潰されている)。失えば、この個体のダンプ以外に戻す手段が無い。

そこから 1 つの規則が出る。

> **最初のフルバックアップは絶対にブーストしない。**
> バックアップが守る対象を消して、そのバックアップを速く取る、は循環している。

実装上、`Ds2Session.fullBackup` には**ブーストの引数が無い**。`false` 既定のフラグですらない —
フラグは急いでいる呼び出し側が立てられるが、存在しない引数は立てられないため。
検証済みの 2 パス取得が済んで初めて `enterFastRead` が使えるようになる。

### 拒否条件 (`buildPreservationPlan`)

| 条件 | 理由 |
|---|---|
| バックアップが無い | 戻す元が無い |
| 2 パス照合されていない | 1 パスは取りこぼしても「それらしいファイル」になる |
| 1 MiB でない | フルキャプチャではない |
| どちらかのサービスブロックが全 0xFF | そのキャプチャはそこまで届いていない |

### 同一 ECU の証明は VIN ではなくバイト比較

最初は「`0x5D50` の VIN 13 バイト」で照合しようとした。**実キャプチャで破綻した** —
あの領域は構造化レコードで、VIN はその**中のフィールド**であり、
実車ダンプ (`hw2001_full.bin`) の `0x5D50+0x40` に読める ASCII はほぼ無い。
推測したオフセットで比較していたら、パディング同士を比べて「一致」と言っていた。

現在の `serviceBlockMatches` は **8 KiB 全体をバイト比較**する。VIN も AIF も ZIF/BRIF も
一度に覆え、どのフィールドも解読する必要が無い。
**除外するのはフラッシュカウンタだけ** — セッションを消費するたびに正当に進むため。

## 3. 速度の正直な数字

| | 9600 | 125000 |
|---|---|---|
| 1 MiB (4232 exchanges) | 約 25 分 | 約 5 分 |

**13 倍にはならない。** 1 チャンクあたり実測 196.9 ms のうち、141.7 ms が回線
(理論値 144.4 ms) で、**約 53 ms は DME 自身の処理時間**。回線速度では縮まない。
`estimateRead()` はこの床 (`DEVICE_TURNAROUND_MS = 53`) を含めて見積もる。

16 KiB の SA0 だけを読むなら節約は 1 分未満で、**8 KiB の消去とフラッシュカウンタ 1 スロットに
見合わない**。UI もそこでは提示しない。

## 4. Android / WebUSB の方が構造的に安全

| | Web Serial (デスクトップ) | WebUSB FTDI (Android) |
|---|---|---|
| ボーレート変更 | `close()` + `open()` | **開いたハンドルへ制御転送 1 発** |
| DTR/RTS | 再オープンで動く | 動かない |
| 読みポンプ | 止めて再開 | 止まらない |

Web Serial には in-place のボーレート変更が無く、切替のたびに他の DS2 ツールが決して起こさない
ポート遷移が入る。**しかも切替を打つのはプログラミングセッション中 = 何かが消えている最中**である。
`webUsbFtdiTransport.ts` はベンダ制御転送 1 発で済むので、この外乱が構造的に消える。

分周値は 3 つだけを監査済み定数として持ち、**モジュール読み込み時に再計算して照合する**
(`assertDivisorTable`)。125000 は `24 MHz / 192` でちょうど割り切れ、baud 誤差ゼロ。

## 5. 実装状況

| | 状態 |
|---|---|
| `fastEntry.ts` — 保全計画・拒否条件・チャンク分割・見積り | **完成・40 tests** |
| `session.ts` — `enterFastRead()` の 3 フェーズ実行 | **完成。書込ロックで停止** |
| `webUsbFtdiTransport.ts` — Android バックエンド | **完成** |
| 実機での実行 | 未 (ロック解除が前提) |

`enterFastRead()` は**最初の 1 バイトが線に出る前に** `assertWriteUnlocked` で止まる。
`session.test.ts` はそれを「テレグラムの送信履歴が空であること」で固定している —
ログインの後に置いた検査は無害だが順序を何も証明せず、消去の後に置いた検査はブリックだから。

## 6. 未実行の検討

- **カウンタ消費**: 1 回の fast entry がスロットを 1 消費するのか 2 か。実機でしか分からない。
- **slave 側の消去は本当に要るか**: TUNER は両方に消去を送るが、そのコメント自身が
  「slave が実際に消えた証拠にはならない (99.3% が 0xFF なので書込も照合も通ってしまう)」と
  書いている。本ツールも 2 発送るが、**それが必要かは別問題として残す**。
- **`0x424152` (recycle-off)**: `0x424150→0xC6` / `0x424151→0xC7` は逆アセンブルで確認済みだが、
  `0x424152` の写像はこちらでは未確認。参照実装が送っているので送っている。
