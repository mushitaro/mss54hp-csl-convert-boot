# region_table — DME が受理するフラッシュ窓 (実測)

CSL 0401 イメージ (`Full 211323000401PD31_TERRA.bin`) から**実測**した、ブートローダが
受理するアドレス窓の全体像。再現は `tools/analysis/region_map.py`。

## どうやって特定したか

`flash_req_parse` (decomp `master/00289c.txt`) を capstone で逆アセンブルし、テーブルの
実アドレスと構造を確定した (`tools/analysis/find_region_table.py`)。

```
00289C  movem.l  d2-d4/a2-a4, -(a7)
0028A4  movea.l  #$3ad6, a1          <- region_table のベース = 0x3AD6
0028CC  lsl.l    #$2, d0             <- d0 = idx*4
0028CE  add.l    d1, d0              <-      + idx = idx*5
0028D0  cmpi.b   #$ff, $1(a1, d0.l)  <- 拡張ワード 0a01: scale=2 => 実効ストライド 10
002920  cmpi.b   #$41, d3            <- 最大 0x41 = 65 エントリ
002938  move.b   #$b0, $2(a0)        <- 範囲外は 0xB0
```

エントリ (10 バイト, ビッグエンディアン): `+0 id | +1 variant | +2 start(u32) | +6 end(u32)`

アドレス解決 (decomp より):
```c
addr_hi = req[4];  if (variant != 0xFF) addr_hi &= 0x0F;   // 上位ニブルは窓の選択に使われる
addr    = req[6] | (req[5] | addr_hi<<8)<<8;
accept iff !(start==0 && end==0) && start <= addr < end
len     = min(req[7], end-addr, 0x80)
```

## 結果 1 — セグメント id は TUNER の実証済み定数と一致する

| id | 名前 (TUNER `Ds2ProgrammingControl`) |
|---|---|
| `0x00` | 読み出し/リニア (`Mss54HpDataTuneLayout.readSegment = 0`) |
| `0x02` | **WriteSegment** |
| `0x06` | **EraseSegment** |
| `0x0E` | **RecyclingSegment** |
| `0x0F` | **FinishSegment** |

## 結果 2 — 固定窓 (variant `0xFF`: アドレスをそのまま使う)

| id | 範囲 | 意味 |
|---|---|---|
| `0x0E` | `0x424150`–`0x424160` | ASCII "BAP".. — TUNER の `RecycleOnlyAddress 0x424151`("BAQ") / `RecycleOffAddress 0x424152`("BAR") がここに入る |
| `0x01` / `0x08` | `0xFF8000`–`0xFF9000` | RAM 窓 (4 KiB) |
| `0x04` / `0x0B` | `0xFFD000`–`0xFFF000` | 内部 RAM / 診断バッファ (8 KiB) |
| `0x05` / `0x0C` | `0x000000`–`0x1000000` | 全アドレス空間 (16 MiB) |
| **`0x03` / `0x0A`** | `start=0x006000, end=0x002000` | **`end <= start` なので常に拒否される = 設計上到達不能** |

> **`0x03`/`0x0A` は「無効エントリ」ではなく、設計されたロック**である。`0x6000` は
> ガード/AIF セクタ (`aif_erase_tail_guard_sector`, key `0xC7`)。**ファーム作者はこの経路から
> ガード域に触れられないようテーブル側で封じている。** 我々の保護域不変条件は、ECU 自身が
> 既に強制している性質と一致する — 我々のガードは二重化であって唯一の砦ではない。

## 結果 3 — variant 窓: **アドレス上位ニブルが窓を選ぶ**

セグメント `0x00`/`0x02`/`0x06`/`0x0F` はいずれも同じ 14 ニブルを持つ (ニブル `0x7`/`0xF` は不在 = 到達不能)。

| ニブル | 0 | 1 | **2** | 3 | 4 | **5** | 6 | 8 | 9 | **A** | B | C | **D** | E |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| サイズ | 8K | 16K | **32K** | 2K | 8K | **448K** | 8K | 8K | 16K | **32K** | 2K | 8K | **448K** | 8K |

`0x0`–`0x6` と `0x8`–`0xE` は**完全なミラー = 2 つの CPU**。

| ニブル | CPU | 内容 | 根拠 |
|---|---|---|---|
| `0x2` | master | **較正データ 32 KiB** | TUNER `Mss54HpDataTuneLayout.master = {0x200000, 32768}` (実車実証済み) |
| `0xA` | slave | **較正データ 32 KiB** | TUNER `.slave = {0xA00000, 32768}`、書込は `0xA02000` |
| **`0x5`** | master | **プログラム 448 KiB** | ← **CSL 変換が書き換える本体** |
| **`0xD`** | slave | **プログラム 448 KiB** | ← 同上 |

例外 1 件: `FinishSegment(0x0F)` のニブル `0x3` だけ 8K (他セグメントは 2K)。

## 交差検証 (これが解釈の根拠)

実車で実証済みの独立した定数 3 つが、すべてこのテーブル解釈で受理される:

| 定数 | 判定 |
|---|---|
| `0xA02000` (erase seg 6 / write seg 2) | OK — ニブル `0xA` 窓 `0x0`–`0x8000`、オフセット `0x2000` |
| `0x424151` "BAQ" (seg `0x0E`) | OK — 固定窓 `0x424150`–`0x424160` |
| `0x424152` "BAR" (seg `0x0E`) | OK — 同上 |

⇒ **解釈は独立に裏付けられた。** 推測ではない。

## 「リージョンは 3 つ」仮説との突き合わせ (正直な報告)

実測は **CPU あたり 7 窓 / 合計 14 窓**。ただし CSL 変換で実際に書くのは:

| # | 窓 | サイズ | 用途 |
|---|---|---|---|
| 1 | master プログラム (ニブル `0x5`) | 448 KiB | 0401 ファーム本体 |
| 2 | slave プログラム (ニブル `0xD`) | 448 KiB | 0401 ファーム本体 |
| 3 | master 較正 (ニブル `0x2`) | 32 KiB | 較正データ |
| 4 | slave 較正 (ニブル `0xA`) | 32 KiB | 較正データ |

= **4 窓**。「プログラム / データ / サービス識別」という**種別**で数えれば 3 だが、
**書込単位としては 4** である。UI の選択肢はこの 4 窓を単位に組む。

## 書込チャンク上限 — 122 バイト (128 ではない)

`flash_req_parse` は `0x80`(128) で切るが、**先に効くのは DS2 フレーミング側**:
DS2 write count の上限が 123、かつフラッシュ書込は偶数長・偶数アドレスを要求するため
**122 が最大の合法値**で、これ以上は上げられない (TUNER `Mss54HpDataTuneLayout.writeChunkSize`
のコメントが根拠と経緯を持つ)。読取 122 とは**別定数として分離すること** — 共有すると
「読取側を伸ばしたら書込側が壊れる」潜在的ブリックになる。

## この文書が確定させたこと / まだ確定していないこと

**確定**: テーブル位置・構造・全エントリ・セグメント id・ニブル→窓の対応・保護域が
ECU 側で封じられている事実・書込チャンクの真の上限。

**未確定 (推測で埋めない)**:
- プログラム窓 (`0x5`/`0xD`) に対する **erase/write が実際に受理されるか** — 本テーブルは
  「アドレスが範囲内である」ことしか保証しない。受理はベンチ実機でしか確かめられない。
- プログラム窓の**消去単位 (セクタ境界)** — NOR のセクタ地図は BIN からは読めない。
- プログラム画像に対する**整合検査の有無と算法**。`checksum_b`/`checksum_s` は
  **フラッシュ署名ではない** (下記) ので、別に同定が要る。

## 訂正 — `checksum_b` / `checksum_s` はフラッシュ署名ではない

当初の計画は「`checksum_b`(seed 0x24)/`checksum_s`(seed 0x1248) = `FLASH_SIGNATUR_PRUEFEN` の実体」
としていたが、**これは誤り**。実際には:

- `checksum_b` の唯一の呼び出し元は `ed_fil_table_restore_from_flash` (`master/03333e.txt`) で、
  **エラーフィルタ表 (0x54C バイト) の 1 バイト整合検査**。末尾 `+0x54C` の格納値と比較する。
- `checksum_s` は逆コンパイル済み 644 関数の中に**呼び出し元が無い**。
- 逆コンパイル済みコードに signature/CRC を名乗る関数は**存在しない** (1,705 関数中 644 のみ
  逆コンパイル済みなので、未逆コンパイル領域にある可能性は残る)。

実務上の含意: **既知で実証済みの整合検査はデータペアの CRC-16/ARC のみ** (slave `0x3FFC` /
master `0xBFFC`、TUNER `checksum/dmeDataChecksum.ts` が実 BIN でバイト一致確認済み)。
プログラム域の整合検査は**未同定**であり、同定できるまでプログラム書込は行わない。
