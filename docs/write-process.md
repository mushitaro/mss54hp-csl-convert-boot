# 書き込みプロセスと UX 評価 — 1 ステップか 2 ステップか

## 結論

**ユーザーから見せる操作は 1 つにする。内部は 2 フェーズ、失敗時だけフェーズ境界から再開。**

理由は 3 つで、いずれも実測に基づく:

1. **4 つのトグルはすべて較正域にある** ⇒ 書く前に最終イメージが確定できる。
   「まず純正 CSL を焼いて DTC を出し、あとで直す」中間状態は**技術的に不要**。
2. **フラッシュカウンタはプロセッサあたり 30 スロットしかなく、書込 1 回が 1 スロットを消費する**。
   2 ステップは**最良でも同数、最悪で 2 倍**を恒久的に消費する。
3. 中間状態(MAP センサ無し・フラップ無しの車に純正 CSL 較正)は、**そこで中断されたら車が
   DTC を出したまま残る**状態。得るものが無いのに、失敗時の着地点が悪くなる。

---

## 1. 線の上で実際に起きること

接続は既存の実証済み経路 (`E46M3CSL_TuningTool/src/lib/dme-link`) と同じ:
**アプリ → WebSerial/WebUSB → K+DCAN → DS2 → DME**。ブラウザから直接叩く (EdiabasLib 非依存)。

```
CONNECT ──> IDENT ──> 互換ゲート ──> [ローカルでイメージ組立・全検証] ──> 1 セッション
                                                                          │
   ┌──────────────────────────────────────────────────────────────────────┘
   │  login (seed/key, accessLevel 5)
   │  ── フェーズ A: プログラム 512 KiB ─────────────────────────
   │    erase  seg 0x06 @ プログラム窓          <- ここでセッションが開く
   │    baud boost 9600 -> 125000 (best-effort, 効かなければ 9600 のまま続行)
   │    write  seg 0x02 x 122 B          master 0x500000 + slave 0xD00000
   │    verify (chunk ごとの verify byte + 読み戻し)
   │  ── フェーズ B: 較正 64 KiB (トグル適用済み) ────────────────
   │    erase  seg 0x06 @ 0xA02000
   │    write  seg 0x02 x 122 B          master 0x200000 + slave 0xA00000
   │    verify
   │  reset -> IDENT で 0401 を確認
   └──────────────────────────────────────────────────────────────
```

- **消去がセッションの入口**である。karter16 の "fast entry" は**読み取り用**(小さな Free
  Identifiers セクタを消して 125000 baud を得る) で、書込経路では最初の実消去がその役を果たす。
- **消去は「窓の種類」単位で両 CPU をまとめて消す。** 参照実装は `0xA02000` へ消去を 1 回送るだけで
  master (`0x200000`) と slave (`0xA00000`) の両方を書けている。NOR は消去なしに書けず、DME は
  未消去なら verify byte 3 を返すので、これは実車で確かめられた事実。
- **プログラム窓の消去/書込が実際に受理されるかは未検証** (`region_table` はアドレスが範囲内で
  あることしか保証しない)。ベンチで確かめるまで、以下の時間見積もりも含めて全部が条件付き。

## 2. 所要時間 (参照実装の実測からのスケール)

参照実装の実測: **64 KiB 書込 = 約 2.5 分** (QUICK)、**約 4.5 分** (FULL = 65,536 B の
読み戻し 122.9 秒を追加)。9600 baud での値。

| フェーズ | 量 | QUICK | FULL |
|---|---|---|---|
| プログラム | 512 KiB (= 64 KiB × 8) | 約 20 分 | 約 36 分 |
| 較正 | 64 KiB | 約 2.5 分 | 約 4.5 分 |
| **合計** | 576 KiB | **約 23 分** | **約 40 分** |

125000 baud への昇圧が保持できれば大幅に縮むが、**保持は保証されない** (参照実装は昇圧後に
キープアライブで応答を確かめ、駄目なら 9600 に落として続行する)。**保守的な見積もりを UI に出す。**

## 3. 決定的な制約 — フラッシュカウンタ

参照実装 `flashCounter.ts` より (実車で確認済み):

- カウンタは Free Identifiers ブロック内 `+0x800`、**プロセッサあたり 30 スロット**。
- **プログラミングセッション 1 回が 1 スロットを消費**し、**埋まると DME はプログラミングを
  受け付けなくなる**。
- リセットは可能だが、**VIN・AIF・ZIF を持つ 8 KiB サービスブロックを両 CPU で消して書き直す**
  操作で、所要 1.5–2 分、専用のガードとバックアップ/復旧手順を要する。気軽な操作ではない。

⇒ **書込回数は有限資源として設計する。** 開発中のベンチ試行も 1 回ずつ減っていく。

> **未確定**: 1 セッション内で消去を 2 回 (プログラム窓 + 較正窓) 行ったとき、消費が
> **1 スロットか 2 スロットか**は測っていない。ベンチでカウンタを前後で読めば 1 回で分かる。
> 1 スロットなら 1 ステップの優位はさらに大きく、2 スロットでも 2 ステップと同数で、劣ることはない。

## 4. 2 ステップ案の評価

| | 2 ステップ (フル → パーシャル) | 1 ステップ (推奨) |
|---|---|---|
| スロット消費 | 2 (確定) | 1 または 2 (未確定だが 2 を超えない) |
| 中間状態 | **DTC が出る状態が実在する** | 無い |
| 中断されたときの着地点 | DTC 状態の車 | 変換前 or 変換後 (再実行で復帰) |
| 1 操作の長さ | 20 分 + 2.5 分 | 23 分 |
| 失敗時の再試行コスト | 較正だけなら 2.5 分 | (下記の再開で同じ) |
| セッション/login の回数 | 2 | 1 |

**2 ステップの唯一の実質的な利点**は「プログラムが焼けたことを確かめてから較正に進める」ことと
「較正だけ失敗したときに較正だけ焼き直せる」こと。これは **1 ステップ + フェーズ境界からの再開**で
そのまま得られる — 既定は 1 操作、フェーズ A が verify を通ったのに B で落ちたときだけ
**「較正から再開」**を提示する (フェーズ B は参照実装が実車で回している経路そのもの)。

一方、2 ステップを既定にすると「中間状態で止まる」経路が**常に**開いてしまう。これは
得るもの (再試行の短縮) を、失う可能性のあるもの (DTC を出したまま放置される車) が上回る。

### 中間状態が本当に不要である根拠

4 つのトグルの対象アドレスは**すべて 64 KiB 較正の中**にある (`docs/variant-targets.md`)。
プログラム 512 KiB は変種によらず同一。したがって:

- 書き始める前に**最終的な較正イメージを完成させられる** (パッチ → CRC 再計算 → 検証)。
- 純正 CSL 較正を一度焼く理由が無い。**焼くのは最初から選んだ変種**。

## 5. トグルについて分かったこと (実測)

### フラップ関連テーブルは 2 枚 (EGAS ファミリは 3 枚)

| テーブル | アドレス | 形 | 役割 |
|---|---|---|---|
| `kf_rf_soll_ask` | `0xDB8A` (master) | 24×20 | **フラップ開時の Alpha-N 加算** |
| `kf_egas_wdk_ask` | `0x8872` (master) | 23×14 | **フラップ開時に選ばれる EGAS WDK** |
| `KF_EGAS_WDK` | `0x83E8` (master) | 23×14 | 通常時 (触らない) |
| `KF_EGAS_WDK_KH` | `0x86A6` (master) | 16×12 | 触媒暖機時 (触らない) |

「3 つ」の記憶は **EGAS WDK ファミリが 3 枚**であることに由来する。そのうち**フラップ固有は
`_ask` の 1 枚**で、フラップ関連テーブルは合計 **2 枚**。
加えて `k_ask_*` 定数 **31 個** (`0x21DA`–`0x2265`, slave) と フラップ DTC **3 件**。

### MAP: 標準 M3 と CSL は「載せ替え」ではなく**負荷経路が違う**

パッケージ内の MSS54HP 較正 46 本を `k_rf_cfg` で分けると、例外なく 2 群になる:

| 群 | 本数 | `k_rf_cfg` | 意味 |
|---|---|---|---|
| **CSL (`PD*`)** | 6 | **`0x12`** | Alpha-N + MAP 積分 |
| 標準 (`J*` / `1601` / `1801` 等) | 40 | **`0x04`** | **`rf_hfm1` = HFM (MAF) 経路** |

**標準 M3 は MAF で負荷を測っている。** CSL は MAF を持たず Alpha-N + MAP。だから変換後に
MAP センサが無ければ MAP 診断が落ちて Alpha-N フォールバックになる — ユーザーの想定どおり。

これは「MAP を使う/使わない」の 3 択に加えて、**`0x04` (HFM を使い続ける) という 4 つ目の道**が
原理的に存在することを意味する。ただし `10-load-path.md` は 0401 での HFM を
**「ハード改造前提・非推奨」**としており、CSL プログラムでの HFM 経路は未検証。**今は出さない。**

### VANOS オフセットは CSL と標準で確かに違う

CSL (`PD*`) 6 本はすべて同一署名で、標準群と異なる:

| 項目 | アドレス | CSL (`PD*`) |
|---|---|---|
| `K_EVAN1_OFFSET` | `0x1802` (slave) | 30 |
| `K_AVAN1_OFFSET` | `0x1BB6` (slave) | 65516 (= −20) |
| `K_AVAN2_OFFSET` | `0xC04E` (master) | 65516 (= −20) |
| `k_rg_avan1_offset` | `0xE6D2` (master) | 20 |

> **⚠ 「標準 M3 の値」をそのまま持って来てはいけない。** 標準較正の同アドレスを読むと
> `K_AVAN1_OFFSET` = 12850 (`0x3232` = ASCII `"22"`)、14135 (`0x3737` = `"77"`) のような値が出る。
> **ASCII が見えている = そのアドレスは標準側では別の物** であり、CSL 0401 の XDF の
> アドレスは**標準プログラムの較正には通用しない**。
>
> したがって「標準 M3 オフセット」トグルを出すには、値を**バイトのコピーではなく物理量として**
> 決める必要がある (Funktionsrahmen で単位と基準を確認する)。**それまでこのトグルは出さない。**

## 6. 提案する画面フロー

```
[1] CONNECT        ケーブル選択 -> IDENT
                   MSS54HP か / 現在の版数 / フラッシュカウンタ残 を表示
                   非互換 (初期 MSS54 等) はここで拒否
[2] BACKUP         現行イメージを吸い出して保存 (非破壊・必須)
[3] VARIANT        MAP: 使う / 後で使う / 使わない
                   フラップ: 有り / 無し
                   (VANOS は実装済み: 読み出し箇所を逆アセンブルで特定。DTC オフは根拠待ち)
                   -> 選択に応じて最終イメージを組み、CRC 再計算、
                      region 受理・チャンク長・保護域を全部ローカル検証
                   -> 変更バイトの一覧 (manifest) を提示
[4] CONFIRM        何をどこに書くか・所要時間・消費スロット数を明示して確認
[5] WRITE          1 セッション: プログラム -> 較正 -> verify -> reset
                   (B で失敗したときだけ「較正から再開」を提示)
[6] VERIFY         再 IDENT + 較正 CRC 照合 -> 完了
```

`[2]` のバックアップは**書込の前提条件**にする (スキップ不可)。`[3]` の検証がすべて通るまで
`[5]` のバイト列を組み立てられない、という不変条件で守る。

| 事項 | 影響 | 確かめ方 |
|---|---|---|
| プログラム窓の erase/write を DME が受理するか | **全体の前提** | ベンチで 1 回 |
| 1 セッション 2 消去のスロット消費 (1 か 2 か) | 1 ステップの優位の大きさ | ベンチでカウンタ前後読み |
| プログラム窓の消去単位 (セクタ境界) | 消去コマンドの回数 | ベンチ |
