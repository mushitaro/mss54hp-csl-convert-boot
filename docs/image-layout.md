# イメージ配置と SP-DATEN — 実測

CSL 0401 の**純正バイトがどこから来て、DME のどこに置かれるか**。すべて実ファイルの照合で確定した。
再現は `tools/analysis/parse_pa.py`、固定は `packages/dme-flash/src/imageLayout.test.ts`。

## 1. 純正 CSL 0401 の在処

SP-DATEN E46 v74 の `data/MSS54/` に、プログラム 11 本・較正 81 本がある。全ファイルの
`ZL_System` / `K_Stand` を読んで CSL を同定した:

| ファイル | system | 参照番号 | stand | 中身 |
|---|---|---|---|---|
| **`7837340A.0PA`** | MSS54HP | `211325000401` | **0401** | **CSL プログラム 512 KiB** |
| **`A7837331.0DA`** | MSS54HP | — | **PD31** | **CSL 較正 64 KiB** |

参照ノートの実イメージ名 `Full 211323000401**PD31**_TERRA.bin` の `PD31` はこの較正セット名。
つまりあのイメージ = **0401 プログラム + PD31 較正**。

## 2. Austausch-Datei は Intel HEX

`.0PA`/`.0DA` は `;` ヘッダ + Intel HEX 本体 + BMW 独自ディレクティブ。

```
;;ZL_System:        MSS54HP
;;ZL_REFERENZ:      211325000401
$REFERENZ 211325000401 M
:020000040050AA          <- Extended Linear Address: 上位16bit = 0x0050
:10000000....            <- データ (type 00)
:10FFF010....            <- ★ type 0x10 もデータ (各64KiBブロックの最終レコード)
:001D501083              <- 長さ0の type 0x10 = 終端
$CHECKSUMME A06A D       <- CRC-16/ARC (ペイロード全体・ファイル順)
:00000001FF
```

### 罠: **レコードタイプ `0x10` はデータである**

Intel HEX 標準に無い型で、各 64 KiB ブロックの**最終 16 バイト**を運ぶ。終端マーカーと誤読すると
**1 ブロックあたり 16 バイト・1 ファイルあたり 128 バイトが静かに落ちる**。しかも落ちるのは実際の
プログラムコードで、セクション長は 65520 と一見それらしく、アドレスも連続したままになる。

**気付けたのは宣言チェックサムだけだった。** だから `paband.test.ts` は 92 ファイル全部を
検証する。長さ 0 の `0x10` は本当に終端。

### アドレスは既に DS2 空間

Extended Linear Address が `0x0050`–`0x0053` (master) と `0x00D0`–`0x00D3` (slave)。
これは **`region_table` のニブル `0x5`/`0xD` そのもの**。純正配布ファイルのアドレスを、
フラッシャにそのまま渡せる。

## 3. 検証: 92 / 92

`data/MSS54` の `.0PA`/`.0DA` **全 92 ファイル**が、自身の `$CHECKSUMME` (CRC-16/ARC) と一致した。
失敗ゼロ。パーサはこれで証明済み。

| 種別 | 本数 | ペイロード |
|---|---|---|
| MSS54 プログラム | 5 | 384 KiB (6 セクション) |
| MSS54HP プログラム | 6 | **512 KiB (8 セクション)** |
| 較正 (MSS54 / HP) | 81 | 32 / 64 KiB |

## 4. フルイメージ配置 (検証済み)

| 種別 | CPU | DS2 アドレス | フルイメージ | 長さ | 検証 |
|---|---|---|---|---|---|
| 較正 | master | `0x200000` | `0x008000` | 32 KiB | CRC スロット `0x0BFFC` が一致 |
| **プログラム** | master | `0x500000` | `0x010000` | 256 KiB | 純正 `.0PA` と 100.0000% 一致 (2 セクション) |
| 較正 | slave | `0xA00000` | `0x088000` | 32 KiB | CRC スロット `0x8BFFC` が一致 |
| **プログラム** | slave | `0xD00000` | `0x090000` | 256 KiB | 同上 |
| **保護域** | master | — | `0x00000`–`0x07FFF` | 32 KiB | ブートローダ/AIF/サービス。**触らない** |
| **保護域** | slave | — | `0x80000`–`0x87FFF` | 32 KiB | 同上 |

各 CPU 512 KiB = 保護域 32K + 較正 32K + プログラム 256K (+ 未使用)。
プログラムは 448 KiB の窓のうち先頭 256 KiB だけを使う。**窓に残りがあっても、SP-DATEN が
運ばないバイトを我々が捏造してはいけない。**

較正 CRC は参照実装と同じ**回転入力**: 上位 16 KiB → 下位 16 KiB (スロット `+0x3FFC` の手前まで)。
実イメージで master/slave 両方が一致し、パディング `FF FF` も期待どおり。

## 5. TERRA 改造の正体 (487 バイト / 0.0929%)

純正 `7837340A.0PA` と参照イメージの差は **524,288 バイト中 487 バイトだけ**。内訳が読める:

| 場所 | 内容 |
|---|---|
| `0xD32482`〜 (slave, 空き `FF` 領域) | **コード注入** (`4eb9 00013868` = JSR 等) |
| `0xD02B63` / `0xD0241B` | 呼び先を `0x013868` → `0x042482` に**フック**(トランポリン) |
| `0x52BEFC`〜`0x52C033` (master) | コードの挿入/シフト (約 0x137 バイト) |
| `0x531B95` / `0xBA1` / `0xBAD` | ASCII **`'5'`→`'3'`** ×3 = 参照番号 `2113**25**000401` → `2113**23**000401` |
| `0x531BE0` | 直後の 16bit 値 `de9b` → `92eb` |

**参照番号のファミリを 25 → 23 に書き換えている。** ファミリ `2113 23` は他の MSS54HP
(1601/1801/2001/2501/2701) と同じで、SP-DATEN に 0401 は存在しない。つまり CSL のプログラムを
「標準 HP 系の版数」として名乗らせている。純正データを橋渡しする我々の方針では、この書き換えを
**するのかしないのかが設計判断**になる (→ §未解決)。

## 6. 未解決 — 推測で埋めていない

- **`0x531BE0` の 16bit 値の正体**。プログラム識別ブロック (`211325000401`×3 + `7837340`×6 + `0000`)
  の直後にあり、TERRA が 3 バイト変更したときに一緒に変わっている。局所範囲の
  CRC-16/ARC・sum・ROL 加算 (`checksum_s` 形) はいずれも**再現しなかった**。範囲がより広いか、
  別アルゴリズムか、そもそもチェックサムでないか — **同定できるまでプログラム書込はしない。**
- **ECU がプログラム域に対して何を検証するか**。ブートローダのアプリ引き渡しは
  `aif_tail_guard_key == 0x66` の 1 バイトのみで画像検証は無い (逆コンパイル済み範囲では)。
- **ファミリ 25 / 23 の使い分け**を DME 側が見るのか。見るなら、標準車に純正 0401 をそのまま
  入れて受理されるかが変わる。
