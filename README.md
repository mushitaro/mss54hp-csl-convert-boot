# MSS54HP CSL CONVERT — 標準 → CSL (OBD / ブートローダ非依存)

TSUNAGI ///M — E46 M3 の **MSS54HP DME** を、標準プログラムから **CSL 相当 (プログラム `0401`)** へ
**OBD (K+DCAN) 経由・車載ブートローダの純正フラッシュ経路だけで**変換するツール。
ベンチ/BDM ブートローダも、WinKFP も要らないことを目指す。

> **このビルドは ECU に書き込めません。** `writeLock.ts` の `HARDWARE_WRITE_ENABLED = false` が
> 破壊的テレグラムの組立を例外で止めます。計画・組立・検証は動きますが、**バイト列は出ません**。
> 解錠は 1 行の変更で、それは「BDM 復旧手段と予備 ECU がある」という宣言に等しい。

```bash
npm install
npm test           # 手元に BMW のファイルが無ければ、要るテストは skip
npx tsc --noEmit
npm run gen:region-table   # 実イメージから region_table を再生成
```

`npm run deploy`（`scripts/deploy.mjs`）。プロジェクトは `wrangler.jsonc` の `name`

## 測定で確定した事実

すべて CSL 0401 実イメージ (`Full 211323000401PD31_TERRA.bin`) と、実車で実証済みの
参照実装 (E46M3CSL_TuningTool) から。テストが数値を固定している。

### DME が受理するフラッシュ窓 — `region_table` @ `0x3AD6`

`flash_req_parse` (master `0x289C`) を capstone で逆アセンブルして位置と構造を確定し、
65 エントリすべてをイメージから生成した (`tools/analysis/`)。

- セグメント id は参照実装の `Ds2ProgrammingControl` と**一致**
  (`0x02` Write / `0x06` Erase / `0x0E` Recycling / `0x0F` Finish / `0x00` 読取)。
- variant 窓は**アドレス上位ニブルが窓を選ぶ**。`0x0`–`0x6` と `0x8`–`0xE` は完全なミラー = **2 CPU**。

| ニブル | 0 | 1 | **2** | 3 | 4 | **5** | 6 | 8 | 9 | **A** | B | C | **D** | E |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| サイズ | 8K | 16K | **32K** | 2K | 8K | **448K** | 8K | 8K | 16K | **32K** | 2K | 8K | **448K** | 8K |

**CSL 変換が書くのは 4 窓**: master/slave の**プログラム 448 KiB** (ニブル `0x5`/`0xD`) と
**パラメータ 32 KiB** (`0x2`/`0xA`)。種別で数えれば 3 だが、**書込単位としては 4**。

### 解釈は実車実証済みの定数で裏付けた

`0xA02000` (erase/write)、`0x424151`/`0x424152` ("BAQ"/"BAR", recycling)、
`0x200000`/`0xA00000` (パラメータ 32 KiB ペア) — **4 つすべてが我々のテーブル読みで受理される**。
推測ではない。

### ガード域は ECU 自身が封じている

`region_table` の id `0x03`/`0x0A` は `start=0x6000, end=0x2000`。`end <= start` は
`start <= addr < end` を絶対に満たさないので、**AIF ガードセクタはこの経路から到達不能**。
我々の保護域ガードは**二重化**であって唯一の砦ではない。

### 書込チャンクは 122 バイト (128 ではない)

ファームの `flash_req_parse` は `0x80`(128) で切るが、**先に効くのは DS2 側**: write count 上限 123、
かつフラッシュ書込は偶数長・偶数アドレス ⇒ **122 が最大の合法値**。読取用の定数とは
**必ず分離する** — 共有すると「読取を伸ばしたら書込が壊れる」潜在的ブリックになる。

`WRITE_CHUNK_MAX` はモジュールスコープの不変条件で守られ、**発火を実証済み**
(124 → "exceeds the DS2 write count cap of 123"、121 → "must be positive and even")。

### 純正 CSL 0401 は SP-DATEN にあり、読み出せる

`data/MSS54/7837340A.0PA` (MSS54HP / 参照 `211325000401` / stand **0401**) が CSL プログラム
512 KiB、`A7837331.0DA` が CSL パラメータ (**PD31**) 64 KiB。参照ノートの実イメージ名
`Full 211323000401**PD31**_TERRA.bin` の `PD31` はこのパラメータセットのこと。

形式は **Intel HEX + BMW 独自ディレクティブ**。**レコードタイプ `0x10` はデータ**で、各 64 KiB
ブロックの最終 16 バイトを運ぶ (終端と誤読すると 1 ファイル 128 バイトのコードが静かに落ちる)。
アドレスは既に DS2 空間 (`0x0050`–`0x0053` / `0x00D0`–`0x00D3` = ニブル `0x5`/`0xD`) なので、
フラッシャにそのまま渡せる。

**`data/MSS54` の 92 ファイル全部**が自身の `$CHECKSUMME` (CRC-16/ARC) と一致することを確認済み
(失敗ゼロ)。BMW はプログラムファイルにもパラメータペアと同じ CRC-16/ARC を使っている。

### フルイメージ配置 (検証済み)

| 種別 | CPU | DS2 | フルイメージ | 長さ |
|---|---|---|---|---|
| パラメータ | master | `0x200000` | `0x008000` | 32 KiB (CRC `0x0BFFC`) |
| プログラム | master | `0x500000` | `0x010000` | 256 KiB |
| パラメータ | slave | `0xA00000` | `0x088000` | 32 KiB (CRC `0x8BFFC`) |
| プログラム | slave | `0xD00000` | `0x090000` | 256 KiB |
| **保護域** | 両方 | — | `0x00000`/`0x80000` から 32 KiB | ブートローダ/AIF/サービス |

純正 `.0PA` は実イメージと 8 セクション中 2 つで **100.0000% 一致**、全体でも
**524,288 バイト中 487 バイト差** (0.0929%) — その 487 が既知の第三者改造。パラメータ CRC も
master/slave 両方が実イメージ上で一致。

### 参考: TERRA 改造の正体

487 バイトの内訳が読める: 空き領域へのコード注入 + 呼び先のフック (トランポリン)、master 側の
コード挿入、そして **参照番号 `2113`**`25`**`000401` → `2113`**`23`**`000401`** (ASCII `'5'`→`'3'` ×3)。
CSL のプログラムを標準 HP 系のファミリ版数として名乗らせている。詳細は
[docs/image-layout.md](docs/image-layout.md)。

### 変種はすべてパラメータだけで作れる — だからプログラムは無改変で書ける

MAP 系の定数と DTC は**すべて master 半分**、フラップ (ASK) 系は**すべて slave 半分**にあり、
どちらも**パラメータ (64 KiB) の中**。**プログラム 512 KiB は 1 バイトも変えなくてよい。**

帰結として、プログラム側の整合フィールド — DS2 selection `0x0C` で報告される `DAT_00041be0`
(DS2 `0x531BE0`) の 16bit 値を含む — は **BMW が配布したままで構成上正しい**。
**そのアルゴリズムを同定する必要が無い。** 再計算が要るのはパラメータの CRC-16/ARC だけで、
これは既知・実装済み・純正ファイル全件で検証済み。

当初計画の「純正 SP-DATEN 橋渡し」は、**プログラムについては文字どおり成立する**。

主要アドレス (パラメータペアのオフセット、純正 CSL の実読値):
`k_rf_cfg` @`0xE5E4` = **`0x12`** / `k_p_saug_diag_min|max` @`0xD2F2`,`0xD2F4` /
`kf_rf_soll_ask` Z @`0xDB8A` (480 セル) / フラップ 3 DTC @`0x6164`,`0x62DE`,`0x62EC` /
`DTC_DF_MAP_PRESSURE` @`0xF420`。詳細は [docs/variant-targets.md](docs/variant-targets.md)。

### 訂正: 純正 CSL はフラップ加算を有効で出荷している

計画では「Karter16 の 0401 イメージは ASK 全ゼロ・フラップ診断削除済み」としていたが、**実測は逆**。
純正 PD31 も参照実イメージも `kf_rf_soll_ask` の 480 セル中 **188 セルが非ゼロ**で、負荷とともに
増加し全開で本表の約 4 %。TUNER ドキュメントのその記述は**別のイメージ**を指していた。
実 CSL にはスノーケルフラップがあるので、有効なのが自然。

### DTC の有効/無効は CTL バイトの bit0

`ed_report` (master `0x033636`) の冒頭が `if ((k_ed_fil_base[err].K_ED_FIL_CTL & 1) == 0) return 0;`。
**bit0 が 0 なら故障は数えられず記憶されない。** 純正 CSL PD31 の 241 レコード中 **94 件が既に
bit0 クリア**で、BMW 自身がこの仕組みで DTC を無効化している。

アドレスは **CSL 0401 でのみ有効**であることを実測で確認した (CSL 6 本は 241/241 のレコード署名が
一致、標準パラメータは master 側の表が別の場所)。ビルダーは書く前に署名を検証し、CSL 0401 でなければ
**拒否する**。

### ⚠ MAP の DTC を消すとフォールバックまで消える

`ed_report` の**戻り値**が MAP の健全性フラグ `p_saug_st` になり、`rf_diag` はそれを見て
Alpha-N フォールバックを選ぶ。DTC を無効化すると戻り値が 0 になり、**DME は MAP を「正常」と
判断してフォールバックを選ばない**。

さらに `rf_diag_lut` (master `0x3D534`) を実読すると `rf_diag_ed_st` は **0/1/2 の 3 値**を取り、
**`ed_st=2` では `k_rf_cfg` に関係なく `RF = rf_p_saug`(MAP 直値)** になる。MAP DTC を無効化すると
インデックスの MAP ビットが落ちないので、**LLS 故障が 1 つ起きただけでこの経路に入る**。

⇒ **MAP の DTC は無効化しない。** 記憶される DTC こそが、全ての故障の組合せで Alpha-N を保証する
入力である。MAP の選択肢は **使う** (`0x12`) と **使わない/後で使う** (`0x02`、**DTC は有効のまま**)
の 2 つで、後者 2 つは同一イメージ。無効化するのは**フラップ 3 件だけ**。

### ⚠ フラップ EGAS 表を 0 で埋めてはいけない

`kf_egas_wdk_ask` は加算ではなく**フラップ開時に選ばれるスロットル開度マップ**。通常表とは
322 セル中 4 セル・x 軸 1 点しか違わず、値は最大 1000。**0 で埋めると、フラップ開と判定された
瞬間にスロットル 0 が指令される**(ポット未装着＋DTC 無効なら実際に起こり得る)。
正しい処理は**通常表の軸と z を ask 表にコピー**すること。`kf_rf_soll_ask` は加算なので 0 が正しい。

### 訂正: `checksum_b`/`checksum_s` はフラッシュ署名ではない

当初の計画は両者を `FLASH_SIGNATUR_PRUEFEN` の実体としていたが**誤り**だった。

- `checksum_b` の唯一の呼び出し元は `ed_fil_table_restore_from_flash` で、
  **エラーフィルタ表 (0x54C B) の 1 バイト整合検査**。
- `checksum_s` は逆コンパイル済み 644 関数中に**呼び出し元が無い**。
- signature/CRC を名乗る関数は逆コンパイル済み範囲に**存在しない** (1,705 関数中 644 のみ)。

**既知で実証済みの整合検査はデータペアの CRC-16/ARC だけ** (slave `0x3FFC` / master `0xBFFC`)。

### ブートローダのアプリ引き渡しに画像検証は無い

`boot_handoff_dispatch` (master `0x30BE`) のゲートは **`aif_tail_guard_key == 0x66` の 1 バイト**だけで、
一致すれば `(*DAT_00004884)()` へ跳ぶ。チェックサム照合は無い。**改変プログラムを止める署名は
(この経路には) 無い**一方、**不完全な画像でも跳んでしまう**ということでもある。

## まだ書けない理由

パラメータと変種については、**組み立てたバイト列を送るトランスポート層がまだ無い**。
そしてブートローダ置換については、危険の所在が当初の想定とまったく違う場所にあった。

### ブートローダ置換 — 何が分かり、何が残っているか

詳細は [docs/bootloader-replacement.md](docs/bootloader-replacement.md)。要点だけ:

- **素性は決着した。** 純正 CSL ECU ダンプ 4 本 (BMW 出荷、2004-12-21) の SA0 は
  CP v1 と 1 バイトも違わない。「標準 M3 に 6/3 バイト当てて CRC 再計算したもの」＝純正である
  ことが実測で証明された。
- **消去単位も確定した。** Am29F400BB のセクタ境界と region_table の窓が完全に一致し、
  ニブル→物理アドレスの対応をファーム自身から復元できた。
  副産物として、**プログラム窓 (448 KiB) の消去はファーム側で明示的に許可されている**ことも分かった。
- **⚠ 引き金は cmd `0x34` ではなくリセットハンドラだった。**
  フラッシュ `0xFFFC` にマジックを書いた瞬間から、DME は電源投入のたびに `0x8000` へ飛ぶ。
  ローダが失敗すれば、**SA0 を 1 バイトも消していなくても** OBD からは二度と応答が返らない。
  ⇒ ローダの**最初の**フラッシュ操作をマジックの消去にすることで、
  最も起こりやすい失敗群を「ブリック」から「一度リセットすれば元通り」に変える設計にした。
- **⚠ ブートローダへの無消去書込は、ファームが受理してしまう。**
  消去は拒否されるが、Finish 後の状態ではニブル `0x1`/`0x9` への seg `0x02` が通る。
  NOR はビットを 0 にしかできず SA0 は消去できないので、**誤って書いたら BDM 以外に戻す道が無い**。
  `telegrams.ts` が両経路で無条件に拒否する。

**ローダとその検証は実装済み** ([docs/bootloader-replacement.md](docs/bootloader-replacement.md) §9-10)。
エミュレータ上で、実車の標準 M3 ダンプから出発して純正 CSL の SA0 にバイト一致で到達し、
SA1/SA2 (VIN・AIF・フラッシュカウンタ) は無傷、注入した各危険では必ず失敗する。

**トランスポート層も実装済み。** シミュレータ相手に、ログインからフルバックアップまで
実際に走る経路として通っている (`session.test.ts`)。

⇒ **M1 (無リスクのフルバックアップ) は実車に向けられる状態**にある。
現行のどのツールも取れない SA0/SA1/SA2 込みの 1 MiB を、2 パスで読んで照合する。
純正 CSL DME を持つ人がこれを走らせれば、コミュニティは無リスクで
権威ある SA0 を公開できる。

残るのは UI と実機での実行。書込は施錠されたままで、
実機へ進む条件は変わっていない: BDM 復旧手段・予備 ECU・安定化電源。
**最初に arm するのはプローブローダ**であって置換ローダではない。

### 次の一歩は非破壊の読み出し

`fullSpaceRead.ts` が seg `0x05`/`0x0C` で **SA0/SA1/SA2 を含む全 512 KiB** を読む。
現行のどのツールも取れないフルバックアップであり、同時に
アドレス方式のベンチ実機検証と、ニブル→物理の実測確認を兼ねる。
**危険な操作の前に、危険でない操作で同じ仮説を試せる。**

## FAST ENTRY の消去後復旧を移植しました

TUNER の `recoverFastEntry` がこちらに落ちていました。**方針は移植して、その隣を落とす** —
今日ずっと直してきたのと同じ形で、しかも落ちていたのが VIN を持つセクタの側でした。

### どの窓を守るのか

`0x4000–0x5FFF`（SA1、CPU あたり 8 KiB）の**消去から復元照合までの間だけ**です。
125000 への切替はこの後なので、**復旧自体も 9600 で走り**、ブーストの成否に依存しません。

ここでホスト側の復旧が成立するのは、2 つの前提が揃うからです:

1. DME は通常ファームを走らせ続け、**DS2 に応答している**
2. SA1 はニブル 0/8 で、**このツールが書いてよい**

### ブートローダ側には作れません

武装後に失敗した DME は **DS2 に一切応答しません**（リセットハンドラは K ライン初期化より前に
マジックを見る）。そして SA0 はニブル 1/9 で、**ファームが消去も書き込みも拒否します** —
ローダが存在する理由がこれです。ホスト側の復旧には、話す相手も、送れる合法なテレグラムもありません。

だから緩和策はローダの中にあります: マジックを先に消す / VBR を RAM のハルトテーブルへ /
RAM 内で消去＋書き込みをリトライ。そして**縮約不能な窓（SA0 消去〜書き込み完了）に対する
唯一の対策がベンチ電源**です。

### 参照実装より 1 つ踏み込みました

TUNER は復元して戻るだけで、操作者の本当の問い —「**VIN は残っているのか**」— に答えません。
こちらは復旧後に全スパンを読み戻してバイト照合し、2 つの結果を**別の文言**で報告します。
次にすべきことが正反対だからです:

- 戻った → 「バックアップと照合してから慎重に進める」
- 戻らなかった → 「**この DME には何も書かない。**まずバックアップから復元する」

プログラミングセッションも閉じます（recycle-off / finish が未送信なら送る）。
リサイクリングを ON のまま放置するのは、実証済み手順が ECU を残す状態ではありません。

**ガードが発火することを証明済み** — 復旧を外すと 2 件落ちます。消去**前**の失敗では復旧が
一切走らないことも固定しています（壊れていないものを書き戻す動作を防ぐため）。

## 検証の根拠と、ログインの位置

### 読み戻しが自分と矛盾していても「検証済み」と言っていました

`fullBackup` は**自分自身と照合するために 2 パス読みます**。1 パスだけの読み出しは、
チャンクを落としても「それらしいファイル」になるからです。`runFlash` はその `image` を
受け取り、**判定を捨てていました**。

結果として「2 パスが食い違ったが、パス 1 はたまたま書き込みイメージと一致した」読み出しが、
操作者には **VERIFIED** と報告されていました。検証の根拠が、検証にならないと分かっている
読み出しだったわけです。

`verified` は 3 つすべてを要求するようにしました — 読み戻しを行い、**2 パスが互いに一致し**、
その結果がイメージと一致すること。真ん中が欠けていて、それが 3 番目を意味あるものにする条件でした。

2 つの失敗は**処方が逆**なので分けて報告します:

- パス同士が食い違った → **読み直す**
- イメージと違う → **書き直す**

ケーブルがチェック中にグリッチしただけで DME を消去・再書き込みするのは、
2 つのうち危険な方を、原因に対処しないまま行うことになります。

**証明**: 判定を捨てるコードに戻すと、専用テストが落ちます。テストは「パス 1 は一致している」
ことも同時に assert しているので、罠の形そのものを固定しています。

### ログインの位置 — 一度間違えました

「IDENT のクリティカルパスから login を外す」つもりで実装しましたが、**前提が誤りでした**。
`fullSpaceRead.ts` が逆アセンブルから記録していました:

> 命令 0x06 は linear 24-bit セグメントを **0xFFD003 のビット 2** で分岐させ、
> これは cmd 0x90 が付与するアクセスビットで、立っていなければ 0xA2 を返す。

つまり**ブートローダ読み出しもバックアップも、本当にログインを必要とします**。
先に読むべきものを読まずにコメントを書いたので、書いた根拠ごと差し替えました。

正しい修正は別の場所にありました。**IDENT (cmd 0x00) はゲートされていません。**
なので拒否されたときに捨てていた情報があります:

- 以前: 生のエラー 1 行。何が悪いのか分からない
- いま: 識別結果は残り、「ケーブル・アドレス・通信速度は正常、アクセスが拒否された」と言える

これは「何も喋っていない」とは**別の問題**で、操作者の次の手が変わります。
拒否後に 8,600 本の読み出しを撃ってファームに 1 本ずつ拒否させることも、やめました。

## 画面が言っていた嘘 — 9 件

施錠を解除する前に、UI の記述を 1 件ずつコードと突き合わせました。**すべて実在しました。**
共通しているのは「測っていない量を報告している」ことで、これは数字が無いより悪い状態です。
操作者はその数字で続行を判断し、**小さい嘘の数字は「問題なし」に見える**からです。

| 画面の記述 | 実際 |
|---|---|
| 「読み戻した SA0 が **8** バイト違います」 | `differingOffsets` は**8 件で打ち切った標本**。全滅した SA0 でも常に 8 と表示 |
| 「書き込んだ **1 MiB** が実機と完全一致」 | 実際に書いて照合したのは **589,824 バイト**。BL とサービスブロックは書いておらず照合対象外 |
| 「1,048,576 バイトを取得、2 パス一致」 | `0x4000-0x4017` の **24 バイトは取得できない**（ファームが 0xFF を返す）。控えにも照合にも入らない |
| 「ここからは SA0 の消去が要り」（master 段） | SA0 の消去はローダが**両方の段で**行う。master 固有なのは「K ライン側を失う」こと |
| slave の REVIEW に `PROGRAM 21132300 -> 21132500` | プログラム番号は **master の SA0 にしかない**。他方の CPU の値を「この CPU の素性」として表示していた |
| 「**5.0** °KW ずれていれば選択が誤り」 | オフセットは 2 つあり、ずれ方は **5.0 と 3.0**。もう片方を見た操作者は 3.0 を見て「合っている」と判断する |
| 「FLASH を押しても何も起きません」 | プログラム段は**実際に seed/key ログインまで行き**、最初の消去で拒否される |
| 「転送はほぼ停止していました」 | **アプリは測っていません**。分かるのは「裏に回った」ことだけ |
| 進捗バーが `ERASE-CALIBRATION` `WRITE-STAGED` | 翻訳は**存在していたのに誰も呼んでいなかった**。日本語 UI が最も危険な数分間を英語で実況 |

### 直し方

数字は**測った側から取る**ようにしました。`differingCount`（標本と別）、`comparedBytes`
（実際に照合したバイト数）を outcome に載せ、画面はそれを表示します。
カムのずれ量は `VANOS_OFFSETS` から**導出**します — コピーに定数を書いたことが、
2 つあるものを 1 つと書いた原因だからです。

進捗ラベルは `Record<BlPhase | FlashPhase, string>` にしました。**テストより強い**からです:
防ぎたいのは「executor に相を足して名前を付け忘れる」ことで、テストは新しい id の存在を
教えてもらう必要がありますが、コンパイラは既に知っています。実際に相を 1 つ足すと
日英両方でビルドが落ちます。

削除: どこからも参照されていないコピー 5 件。**出荷されているように見える文字列は、
出荷されているものとして保守されます。**

**ガードが発火することを証明済み** — 標本打ち切りを戻すと 1 件、相の追加で型が 2 件落ちます。

## プローブ段 — 最初に武装するものを最小にする

マジックを書いた時点で後戻りはできません。リセットハンドラは SIM・スタック・K ライン
のいずれよりも先にマジックを見るので、ローダが動かなければ **SA0 が無傷のままでも**
DS2 には二度と応答しません。**リハーサルは存在せず、最初の武装が最初の実行です。**

選べるのは「何を最初に武装するか」だけです。そこで工程の先頭に、ブートローダに一切
触れないプローブ段を置きました。`tools/loader/probe.s` はマシンの立ち上げだけを行い、
**最初のフラッシュ操作で自分のマジックを消し**、ウォッチドッグが DME を再起動します。

この ECU について分かること（エミュレータでは議論しかできない 4 点）:

- リセットハンドラが 0x8000 のローダに実際に到達すること
- RESET 命令直後の状態から SRAM アレイを有効化できること
- RAM にコピーしたスタブが実行されること
- リセット時のチップセレクト設定のままフラッシュ書き込みが成功すること

**接続できたこと自体が最初の結果です。** リセットハンドラは K ライン初期化より前に
マジックを見るので、DS2 が応答する DME は既に自分でマジックを消しています。
4 バイトの読み戻しはその直接確認です。

### ラベルではなくバイトで判定します

プローブと置換は、電源投入までまったく同じ操作です（同じ消去・同じ 32 KiB・同じマジック・
同じ不可逆性）。違うのは**中身**だけなので、`validateBlReplace` は plan のラベルを信用せず、
**実際に送出されるバイトからブートローダイメージの有無を再導出**します。

「プローブ」と名乗りながら SA0 イメージを積んだセクタは、このツールが出しうる最悪の
取り違えです — ブートローダに触れないと約束した画面の裏で SA0 書き換えが武装され、
操作者は実行されるのとは違う操作に同意することになります。逆向き（置換なのに中身が空）も
同じ理由で拒否します。SA0 に 0xFF を 16 KiB 書き込むことになるからです。

プラクティスの ECU も直しました。以前は無条件にイメージ領域を SA0 へコピーしていたので、
プローブを走らせると**消去済みフラッシュを SA0 に書き込んで「ブートローダを置換した」と
報告**していました。ブートローダに触れないと言う唯一の画面で、です。

**ガードが発火することを証明済み** — バイト判定を無効化すると 2 件、プラクティス ECU の
条件を外すと 3 件が落ちます。

### ブラウザで見つけたバグ

RUN 画面がプローブ段に「CSL プログラム + パラメータ」という**別の操作の名前**を付けて
いました。FLASH ボタンの真上です。原因は 2 種類しかなかった頃に書かれた二項三項演算子で、

`vitest.config.mts` に web 側の alias を追加しました — これが無いために

### 参照実装との差分監査 — 移植で落とした構造

`TuningTool` は実車をフラッシュした実装です。このアプリは**その移植**であるはずでしたが、
移植の過程で参照実装が既に持っていた構造を潰しており、バグはそこから出ていました。
以下はすべて、テストが落ちて見つけたのではなく、**両者を並べて読んで**見つけたものです。

| 参照実装 | この移植 | 結果 |
|---|---|---|
| `purge()` と `recoverRead()` は別物。`resyncTransport()` が `hasReadError()` で選ぶ | 両方を `drain()` 一つに畳んだ | ライン異常でポンプが停止したまま復帰しない |
| `peekReadError()` は**ラッチを消さない** | `read()` がラッチを消費 | 「異常あり」の問いに、死んだループが「健康」と答える |
| 遅延 → resync の順 | resync → 遅延の順 | 消した直後のバッファに DME の遅延応答が着弾し、次の試行を壊す |
| 異常後は `400ms × 試行回数`（計 4 秒） | 一律 `300ms × 試行回数` | 線が荒れた後、自動再試行が全部ゼロ秒で焼き切れる |

| 長さバイトを信じる前にアドレスを検査 | `declared > 0xff` を 1 バイト値に対して検査（**絶対に発火しない**） | 枠外応答が最大 253 バイトを飲み込み、以降が 1 フレームずれる |

| 受信は待機（parked waiter） | `setTimeout(2)` ポーリング | クランプが 1 交換につき 3 回乗る。**125000 に上げても速くならない** |

すべて移植しました。**ガードが発火することを証明済み** — 7 件のバグを 1 つずつ戻して実行した結果:

```
retry order reversed                    2 failed
flat backoff, no escalation             1 failed
purge where the reader needs rebuilding 1 failed
no write retry                          1 failed
```

エコー判別は**物理**であって発見的手法ではありません。K ラインに割り込むデバイスは線を**下げる**

前者は再試行では直らず、後者はケーブルを見に行っても無駄です。

### ウェイクロック

FT232R の受信 FIFO を吸い出しているのはメインスレッド上のループだけで、9600 で約 267 ms の
余裕しかありません。バックグラウンドのタブは絞られ、凍結されることもあります。
**1 時間の読み出し中に画面が消えるとチップがオーバーランします。**

画面点灯は快適さではなく読み出し完走の前提条件なので、`busy` の間だけ保持します。イグニッション待ちも
`busy` です — 操作者が車の前でアプリを手に持っている、画面が消えて困る瞬間そのものだからです。

API が無い・拒否される・システムが解放する、のいずれも失敗にしません。**保持できていることは、
バックグラウンドに回らなかった証拠ではありません** — それを報告するのは既存の背面化検出です。

### SPEED — 実際に FAST ENTRY を実行します

プログラム段の RUN は、FAST ENTRY を選んでいれば `planFlash` の前に `session.enterFastRead()` を
呼びます。以降の消去・書き込み・読み戻しはすべてそのリンク速度で走ります。

`enterFastRead` は**消去前は throw せず `false` を返す**契約です。バックアップの Free Identifiers
セクタが空、実機のサービスブロックがバックアップと違う、保存範囲が読めない — いずれも 9600 のまま
続行します。消去が始まったあとの失敗だけが throw し、その場合は「サービスブロックが無事か確認する
まで書き込むな」というメッセージとともに**段全体を中止**します。

`false` は 2 つの異なる結末を含みます（消去前に辞退／消去・復元・照合まで済んだがレート変更が
できない）。UI は「125000 に届きませんでした」とだけ言い、どちらだったかはログが持ちます。

**書き込みが施錠されているビルドでは FAST ENTRY は選べません。**消去を伴うからです
(PRACTICE では選べます)。以前は選べてしまい、実行時に予期しない消去エラーで落ちていました。

所要時間の表示は**書き込み後の読み戻し照合**（1 MiB × 2 パス）についてのもので、
9600 で約 62 分、125000 で約 19 分です。`estimateRead` の既定チャンクが `0xfe`（プロトコル上限、
誰も送らない）だったため、以前は実際の半分強の値を出していました。既定を `READ_CHUNK_MAX` に
直し、交換回数をプランの定数と照合するテストで固定しています。

**ブートローダ段に PATCH と SPEED はありません。**ブートローダにパラメータは入っていません。
そしてFAST ENTRY は*バルク読み*を速くするためのもので、
バックアップ以降で残るバルク読みはプログラム段の読み戻しだけです。ブートローダ段が読むのは
staged セクタ 32 KiB と SA0 16 KiB で、ブーストしても 1 分未満しか縮まないのに 8 KiB の消去を
払います。**払えない選択肢を出していました。**

**仕事は 3 段**で、`PLAN` がその全体を出します。

| | 段 | 導出 |
|---|---|---|
| 1 | slave ブートローダ | SA0 の operand から |
| 2 | master ブートローダ | 同上 |
| 3 | CSL プログラム + パラメータ | **導出できない** — 版はパラメータ側にあり読んでいないので、このセッションで走らせたかどうかで判断 |

1 段終わるごとに**自動で再 IDENT して次の段へ戻ります**。手作業として残るのは
**イグニッションの入れ直しだけ**で、これはソフトウェアにはできません
(`onPowerCycle` で止まり、`POWER CYCLED` を押すまで待ちます)。

3 段目が、これまで導線に無かった「パッチオン」です。書くのは各 CPU のプログラム 256 KiB と
パラメータ 32 KiB。

### PATCH — 車両の装備

純正 CSL は **MAP センサ**と**スノーケルフラップ**を装備しています。このツールが変換する標準 M3 は
**どちらも持っていません**。純正のまま書くのは正しい選択です (その分の故障コードが入るだけ)。
装備に合わせてパラメータを編集するのも正しい選択です。**どちらも既定にできない**ので、
SPEED と同じく**未回答から始まり、2 つとも答えるまで先に進みません**。

| 回答 | 書き込むもの |
|---|---|
| MAP 装着 / フラップ装着 | 純正 CSL のまま。**1 バイトも変更しません** |
| MAP 非装着 | `k_rf_cfg` を 1 バイト。アルファ N のみ |
| フラップ非装着 | フラップ用アルファ N 加算をゼロ、EGAS マップを通常側と同一化、フラップ故障 3 つを無効化 |
| 両方非装着 | 7 箇所 / 198 バイト。チェックサムを再計算 |
| カム = 標準 M3 | 2 語 4 バイト (`K_EVAN1_OFFSET` / `K_AVAN1_OFFSET`)。チェックサムを再計算 |

#### カムシャフト — この 1 項目だけ出所が違います

VANOS オフセット 2 語 (pair `0x1802` / `0x1BB6`、スレーブ半分)。**ファームウェアの読み出し箇所を
逆アセンブルで特定済み**:

```
slave 0x0A4DF2:  d0 79 00 08 98 02    add.w $00089802.l,d0
slave 0x0A5E0C:                       add.w $00089BB6.l,d0
```

周辺は歯数 × 60 (6.0 °KW/歯) から区間基準を引き、この語を足し、−15 を足して実測カム位置にします。
つまり**実測カム角への加算トリム、単位 0.1 °KW** — 単位は定義ファイルの名前ではなく演算から出ています。
20 バイトの同一構造が 64 KiB 中**ちょうど 2 回**しか現れず、これが S54 のデュアル VANOS 2 系統です。

**確定していないこと。UI もここでは何も主張しません:**

- **どちらが吸気でどちらが排気か。** 名前は 1 系統の定義ファイルに遡るだけで、独立した 2 つの証言では
  ありません。コード内では `A` / `B` と呼びます。2 語は常に一緒に動くので、答えは要りません。
- **カムが物理的にどちらへ動くか。** これはセンサのゼロ点補正で、閉ループ (`IST = raw + OFFSET + ADAP`)
  の内側にあります。カムは**数値と逆**に落ち着きます。進角・遅角の語は UI に出しません。
- **VANOS 学習が打ち消すかどうか。** アイドルで学習がオフセットを吸収してしまう可能性があります。未解決。

**純正 6 版はすべて +30 / −20 で、BMW は標準カム版を出していません。**標準 M3 の値 (−20 / +10) の出所は
コミュニティのバイナリ 1 本だけで、しかもそのファイルは**パラメータのチェックサムが不正**です
(2F81 と記録、実際は F337 — 2 語を書き換えて再計算しなかった)。本ツールは再計算するので、
書き出すものは元ファイルより整合しています。

> **2 本の差が「1 MiB 中 4 バイト」なのは証拠ではありません。**それは再計算されなかった手編集の副作用で、
> 正しく作れば差は **6 バイト** (2 語 + チェックサム) です。同定は読み出し箇所と構造署名に依っており、
> 差分が無くても成立します。

**選択を誤っても故障コードは出ません。**MAP とフラップは誤りを故障コードで知らせますが、カムは何も
知らせません。UI は両方の選択肢に警告を出し、既定を持ちません。

**MAP の故障コードは意図的に有効なまま**にします。これが入っていることで、他の故障が出ても
充填量の計算がアルファ N から外れません。消すと外れる組み合わせが残ります。

`spDaten.test.ts` が 6 版 × 4 通りすべてで、変更が**パラメータ窓の外に 1 バイトも出ない**ことと、
`verifyManifest` に迷子バイトが無いことを固定しています。

**6 つの版は同梱しています** (`packages/web/public/spdaten/`、gzip 645 KB)。プログラム
`7837340A.0PA` と 6 つのパラメータを、**改変せずそのまま**置いています — アプリが書くバイトが、
テストが純正ダンプと照合しているバイトと同一であることを保証するためです。

Service Worker が precache するので、**電波の無いガレージでも版を選べます**。それがこのアプリの
使われ方なので、操作者に SP-DATEN を探させる設計は間違いでした。別のパッケージを使いたい場合の
読み込み口は残してあります。

| ZL_REFERENZ | K_V1 | ZB |
|---|---|---|
| …PD11 | E46-M3-CSL-EOBD Vmax abgeregelt | 7.837.328 |
| …PD1D | E46-M3-CSL-SA861 Vmax abgeregelt | 7.837.332 |
| …PD1J | E46-M3-CSL-Japan Vmax abgeregelt | 7.837.336 |
| …PD31 | E46-M3-CSL-EOBD SA231 | 7.837.330 |
| …PD3D | E46-M3-CSL-SA861 SA231 | 7.837.334 |
| …PD3J | E46-M3-CSL-Japan SA231 | 7.837.338 |

**表を持ちません。**`.0DA` の `K_V1` をそのまま出します。表はファイルから乖離しますし、
実際このリポジトリの旧メモは 7837329 を「Vmax 無制限」と記録していましたが、
ファイルには `Vmax abgeregelt` — **制限あり** — と書かれています。ファイルが正です。

CSL かどうかはファイル名ではなく宣言された `ZL_REFERENZ` (`21132500…`) で判定します。
CSL 以外は「使わない」と件数を出します — MSS54 フォルダには E46 の全ビルドが入っているので、
黙って 6 件に絞ると、どの 6 件なのか操作者に分かりません。

SP-DATEN は同梱していません。BMW の配布物なので、操作者が自分のものを渡します。

バックアップは 2 択で、**どちらも「1 MiB を何かと突き合わせる」**という同じ形をしています。
違うのは基準をどこに置くかだけです。

| | 基準 | 読み出し | 時間 |
|---|---|---|---|
| 2 パス照合 | 2 回目の読み出し | 2 回 | 約 27 分 |
| 控えと照合する | 保存済みファイル | **1 回** | 約 14 分 |

「1 回読むだけ」はありません。**1 回の読み出しは、比較する相手があって初めて検証になります。**
相手のない 1 回は何も証明しないので、選択肢として存在しません。

読み込んだファイルは `verified: false` で入ります。ファイル名の `_verified_` は
**他人の画面で起きた出来事**であって、このアプリが見た証拠ではないからです。
`VERIFY` を押して全域を実機と照合するまで先へは進めません。

照合は 2 段。まずサービスブロック 8 KiB だけを比較し(別 ECU ならここで 30 秒で判り、
14 分を無駄にしない)、通ったら 1 MiB 全部を `compareReads` で突き合わせます。

差分は**セクタ名で報告**します。`master calibration (SA3)` なら「同じ車だが取得後に
書き換えられた — 復旧元としては古い」、`service block (SA1)` なら「別の ECU」で、
操作者にとって意味がまったく違うためです。どちらも拒否ですが、対処が違います。

`REVIEW` で全設定・SA0 の差分・後戻り不能点を提示し、確認にチェックして初めて
`FLASH` が押せるようになる。**現在は書込ロックにより `FLASH` は
`buildStagedSector` の時点で拒否される** — 実機には 1 バイトも出ない。
`LINK`〜`BACKUP` は実車に対してそのまま動く。

ガイド領域と操作領域の高さ比は **φ (61.8 : 38.2)**。実測 1.6178。読む量が多いのはガイド側で、
下 38.2% は電話を持った親指が既にある場所 — 30 分動く操作のハブはそこに要ります。

置換する CPU は**選ばせません**。順序は 2 つの理由が同じ向きを指して決まります
(`conversionStages`、7 tests): slave の差分はビットを落とすだけで消去が要らない可能性があり、
かつ **DS2 を喋っているのは master** なので、slave を先にすれば失敗しても観測できます。

### 画面を裏に回さないこと (実測)

タブが裏に回ると Chrome は `setTimeout` を約 1 秒に丸めます。**要求 8 ms に対して実測 946 ms。**
WebUSB バックエンドの受信ポーリングは 2 ms 刻みなので、応答待ち 2000 ms の読み出しは
1000 回ではなく **2 回**しか試せません。裏では転送が遅くなるのではなく、**失敗します**。

アプリはこれを検出して赤で告げます。**転送中でも表示します** — 操作者が画面に戻った瞬間に
見るのは「理由もなく這っている進捗バー」なので、終わるまで黙っていては説明になりません。
`visibilitychange` は「変化」でしか発火しないため、busy の遷移ごとに `document.hidden` も
サンプリングします(最初から裏で始めた場合はイベントが一度も鳴らないので)。

`LINK` のハブ下に `PRACTICE`。ケーブル無しで最終確認画面まで通せます。

電源を入れ直すとマジックを見て、armed ならローダを走らせ、マジックを先に消してから SA0 を

### 書込ロックは 2 段で、効いているのは片方だけ

| | 何を止めるか | 例外 |
|---|---|---|
| ビルド門 (`assertWriteUnlocked`) | バイト列が**存在すること** | `withSimulatedEcu` の中では開く |
| **ハードウェア門** (`assertHardwareWriteUnlocked`) | バイト列が**送られること** | **無し** — `transport.simulated` だけで決まる |

安全性を担保しているのは後者だけです。判定はトランスポート自身の申告で、ケーブルを叩く
トランスポートはこれを立てません。**上位層のフラグ・引数・スコープでは実機に届きません。**
`writeLock.test.ts` が両方を固定し、パッケージ内で `simulated: true` を書いているファイルが
`practiceEcu.ts` ただ 1 つであることも grep をテストにして固定しています。

ダウンロードされるファイルは `PRACTICE_NOT-A-CAR_…` から始まります。`EXIT PRACTICE` は
バックアップも選択もログも捨てます。

### PWA として

Android の Chrome で開いて「ホーム画面に追加」。**https が必須** — WebUSB は secure context に
しか出ていないので、ビルドした `index.html` を端末のファイルから開くことはできません。

| | 方針 | 理由 |
|---|---|---|
| ナビゲーション | network-first (3 秒でフォールバック) | 中身は安全規則そのもの。工具箱に眠っていた端末が古い規則で走ってはいけない |
| `/assets/*` | cache-first | 内容ハッシュ名なので陳腐化しようがない |
| `/spdaten` `/program` `/bootloader` | cache-first | ビルドごとに固定。ネットワークが HTML（Pages の SPA フォールバック）を返したら保存せず 404 |
| `/_gate/*` `/api/*` | 触らない | サインインの往復と API をキャッシュから答えない。ナビゲーションより先に除外 |
| 更新 | `skipWaiting` **しない** | フルバックアップは 30 分。走っているページの下でワーカーを差し替える価値は無い |

更新の取得は、全ファイルが 2xx・同一オリジン・ゲートを経由しない・拡張子どおりの型、のときだけ成功します。
一つでも外れたら何も保存せず、今のビルドのままです。ケーブル接続中と操作中は、更新のダウンロード自体をしません。

ランチャーのアイコンは M ICON の `migration`（`tsunagi-m3/scripts/m-icons.mjs` で `public/icons/` に書き出し）。
DME を CSL のプログラムへ移す道具なので MIGRATION、という運営者の決定（2026-09-23）です。以前の `modification` は取り違えでした。
ワークス版のビルドは dev セットを付けます。`npm run icons` が作るのはアプリの中のマークで、ランチャーには使いません。

新しいビルドが待機したらハブの下に `UPDATE` が出ます。**「再読み込みしてください」ではありません** —
同一タブの再読み込みではクライアントが解放されず、待機中のワーカーは待機したまま、古いビルドで
戻ってきます(デプロイ先で確認)。従えるのに効かない指示は、効かないことが分かりにくいぶん最悪です。

ヘッダ右にビルド ID (UTC・秒精度)。分精度だと同じ分内の 2 回目のデプロイでワーカーがバイト一致し、
**更新が黙って出荷されません**でした。ワークス版では、その列の一番上に `WORKS` の札が出ます（押せる操作ではなく、本番には出ません）。
